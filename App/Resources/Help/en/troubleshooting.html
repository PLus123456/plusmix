Troubleshooting

Look in three places first: the one-line message on an input cell (that input's own state, Inputs › Input states), the tooltip of the Record / Stream buttons in the bottom bar (every route's state and why it couldn't start) together with the Stream / Recording Status window (each route's last error and its drops and reconnects), and the notices / reminders at the right of the status line (outputs and system-level events). Cells in error and outputs that couldn't start name the cause and the next step; a "No signal" cell shows the reason the input itself reports on a second line (cut short if long; the tooltip has it all) — compare with §2. This page groups them by symptom. Input messages come from the engine and are in Chinese in this version; below they are quoted in Chinese with an English gloss.

3. Disk

Status lineBehaviour
"Recording n: x MB free on disk"Warning below 1 GB; still recording
"Recording n: x MB free on disk, below the 200 MB minimum"Without a fallback folder: only that recording stops; streaming and rendering continue. Change the minimum in Settings › Advanced › Free space minimum (or with the launch argument --record-min-free-mb)
"Recording n: disk full (…)"Full: written fragments are kept, that recording stops
"Recording n: disk full, switched to the fallback directory: <file name>"The disk ran full; with a fallback folder (Settings › Advanced, or --record-fallback) recording continues there
"Recording n: x MB free on disk, below the y MB minimum; switched to the fallback directory: <file name>"Below the minimum (the disk isn't full yet); with a fallback folder recording continues there too
"Recording n failed to start: …"Folder not writable / missing; fixing the folder retries automatically
"Recording n failed: …"The recorder itself failed (encoder, format and the like, or another write error with enough free space): only that recording stops and it does not move to the fallback folder; see the reason. Its switch stays on and it shows a red "Couldn't start", and changing the settings doesn't retry it: click it in the bottom bar's Record ▴ (stop just this route) to stop it, and start it with the next recording
"…; fallback folder: this route's picture branches are all taken (input n allows at most 4 ISO / Aux), so it did not switch and this recording stopped"An ISO route needs one more picture branch to move to the fallback folder, and all 4 branches of that input (ISO / Aux external displays / NDI® outputs with that input as source) are taken: that recording stops (it never records PGM instead). Remove some ISO / Aux uses and record again
"…; the fallback directory failed too: …"The fallback folder can't be created (a missing one is created first) or written, or the recorder can't start there: that recording stops; choose another fallback folder in Settings › Advanced
A line followed by " — saved: file name, n frames / x s"Stopped for being below the minimum, or an ISO recording whose input was removed: the first half is why, the second half says the file has been finalised and is ready to use
"ISO input n does not exist or has no free branch (at most 4 ISO / Aux per input)"The input being ISO-recorded is gone, or it already feeds 4 ISO recordings / Aux uses (external displays and NDI® outputs showing that input): remove some and record again
"Recording n failed to finalize: …"Writing the index at stop failed; the fragmented .mov stays playable. "Recording n failed to finalize: notRecording" right after "Recording n: disk full (…)" or "Recording n failed: …" belongs to that same stop (the recorder had already failed; this line is program wording, a known issue): the line before it says why
Record in the bottom bar records nothing; notice "No route takes part in recording"Every recording's "Take part in recording" is off, or the PGM row on the ISO page is unchecked and no input is checked: turn on the routes you want
A recording's file name got -2, -3 appendedA file of that name was already in the folder when recording started (no time in the pattern, recording again within the same second, stopping and starting right away…): the new one gets another name and the old recording stays as it was (Outputs › Recording)

Free space is measured on the recording's own volume. A killed process recovers the .mov up to the last 1 s fragment (E6 allows at most 2 s loss).

4. Streaming

Bottom bar / Streaming page / API stateMeaning
"Stream · Connecting", "Connecting (attempt n)" (the API's state alternates between connecting and backoff; it is backoff while waiting for the next attempt)Never connected yet: server unreachable, wrong address or path. A local MediaMTX only accepts the paths in its configuration (the repository's scripts/mediamtx.yml has s1 / s2 / s3 / srt1, with an empty key); any other path stays connecting. Servers such as SRS and nginx-rtmp that reject the authentication through a callback simply drop the connection without saying why, which looks the same: check the server's log, and whether "Authentication…" uses the query-string method with the right parameter names and credentials (Outputs › Stream authentication). The destination is locked while its switch is on: turn it off before fixing the URL
Stays "Connecting (attempt n)", and the last error is "连接失败：连接超时（服务器没回）" (connection timed out, the server didn't answer)The other end accepts the connection but never answers (the port is open but it isn't a streaming service, the service is stuck, or a load balancer accepted it for a dead backend): each attempt is closed when the connection timeout runs out (a fixed 5 s, no setting) and retried with back-off of 1, 2, 4… s (up to "Max retry interval n s"). Stopping while connecting or waiting for the next attempt stops at once. Check the address, the port, and whether the server is alive
The last error is "连接失败：连接被拒（这个地址和端口上没有服务器在听）" (connection refused: no server listening on that address and port) / "连接失败：找不到主机（域名解析失败）" (host not found: DNS lookup failed)Nothing listens on that port (server not running, wrong port) / the host name is wrong or can't be resolved from this Mac: start the server, or fix the URL (turn the switch off first if it is on). The underlying library's own wording is in the system log (§9)
The last error is "连接失败：发布被拒：…" (publish rejected) / "连接失败：服务器拒绝连接：…" (the server rejected the connection)The server said no (its status code and description follow): usually a wrong stream key / path, or the server won't take this stream; unless it is an authentication failure it keeps retrying with back-off
The last error is "连接失败：RTMP 协议错误：AMF0 嵌套过深" (or "…元素过多"; RTMP protocol error: AMF0 nested too deep / too many elements)The server sent a malformed reply in the first two rounds of Adobe authentication (a normal streaming server doesn't): it keeps retrying with back-off; make sure the URL points at your own server (the first item of §10)
"Stream · Reconnecting (attempt n)" (state alternates between connecting / backoff too)Was live, then dropped: exponential back-off, retrying forever; the wait between attempts is capped by "Max retry interval n s" (30 s by default); resumes with a keyframe. If the server rejects the authentication on a reconnect, it stops (see below)
Dark red "Stream · Couldn't start" in the bottom bar ("Stream · k in trouble" with several switched on), tooltip "name: Couldn't start — reason", status line "Stream n failed to start: …" / failedCouldn't start: unknown scheme (only rtmp / rtmps / srt), malformed address, no server. The destination's section on the Streaming page shows the reason: fix the URL (Return or leave the field) and it retries automatically, or "Turn Off This Destination"; healthy destinations are not affected, and the main Stream button only retries the ones that couldn't start or failed
Status line "Stream n failed to start: No URL", the destination's section on the Streaming page "Couldn't start: No URL"Empty address in the output settings
Dark red "Stream · Failed" in the bottom bar ("Stream · k in trouble" with several switched on), status line "Stream n authentication failed (wrong user name or password) and stopped: …"; the destination's section on the Streaming page says "Failed: …", in the status window it is "Failed" and its last error starts with "鉴权失败（用户名或密码不对）" (authentication failed (wrong user name or password))The server rejected the credentials: a wrong user name / password with the Adobe method; a wrong user name / password / parameter name with the query-string method on MediaMTX; or the wrong method — MediaMTX wants a query string after the URL but got the Adobe method (the last error shows NetStream.Publish.Unauthorized). It stops on that attempt and doesn't retry (SRS and nginx-rtmp rejecting through a callback don't end up here; see the first row). The destination's section on the Streaming page is not locked then: correct it in "Authentication…" (methods: Outputs › Stream authentication), then click the section's "Retry" or the Stream button in the bottom bar — fixing it doesn't retry by itself
On another Mac the show's "Authentication…" says "No authentication" although the URL clearly carries query-string credentialsThe query string uses custom parameter names, and those are only remembered on the Mac that saved them. Streaming works as usual; to edit the authentication, choose "Query string" in the form and fill in the original names once (Outputs › Stream authentication)
The last error starts with "鉴权失败（服务器要用户名和密码，地址里没写）" (the server wants a user name and password and the URL has none; the status line still says "wrong user name or password")The server wants Adobe authentication and the URL has no Adobe-method credentials (none entered, or entered with the query-string method): enter them in "Authentication…" with the Adobe method, then retry
The status line / last error contains "鉴权失败（服务器要的鉴权方式不支持）" (method not supported)The server wants Limelight (llnw) authentication, which this version doesn't support; it stops without retrying too
You want to know how often and when a stream dropped, and whyThe Stream / Recording Status window: the Disconnects / Reconnects columns count them, and the events list "Disconnected: reason → Reconnecting (attempt n) → Reconnected" with times
SRT with a passphrase doesn't connectThe passphrase may only use letters, digits and - . _ ~, 10–79 characters; one that doesn't match the server's stays "Connecting (attempt n)" (it isn't recognised as a wrong passphrase)
Frames increase but the player shows nothingCheck stats.encoder[].dropped (network drops): non-keyframes are dropped first when bandwidth is short; lower the bitrate (a lower "Quality" on the Streaming page); keep "Total upload" at the bottom of the page under half your upload bandwidth
Local MediaMTX receives no SRTIts SRT port must bind IPv4 (srtAddress: 0.0.0.0:8890; the repository's scripts/mediamtx.yml already does); RTMP is unaffected

6. Picture and sound

SymptomWhat to check
Status line "Dropped" (missed_render) increasingRendering missed ticks. Usual causes: another app saturating the GPU, thermal throttling, a covered multiview window lowering the refresh. On an idle machine it stays 0
Frames start dropping after nobody touched the Mac for a whileWhen the user is "idle" macOS delays real-time thread wake-ups. While the engine runs PlusMix itself prevents system sleep, App Nap and display sleep (Settings › Performance & Power, both on by default), so normally nothing else is needed. Unattended runs with the lid closed or the screen locked should still run caffeinate -u -i -d -s as well: the app can't prevent sleep on lid-close or a manual lock, and can't declare "user is active" the way -u does
Audio and video out of syncInput Settings › Audio › Audio delay compensation (0–500 ms) for the capture device's own offset; the engine's alignment delay (default 2048 frames = 42.7 ms) is in Settings › Show Audio and takes effect only after "Apply and Restart Engine" (which stops recording / streaming; it asks first)
With a compressor / limiter on Master, the whole picture (monitors, external displays, multiview) runs a few tens of milliseconds lateExpected (monitor sync): the picture is delayed by Master's effect latency (up to about 35 ms), so speakers / headphones match it; recording / streaming / NDI® follow the same timeline. The status window shows "Video delayed n ms" at the bottom
With a compressor / limiter on Bus A / B, the channels they feed are slightly behind the pictureThe picture follows Master's delay only; the extra delay of Bus A / B is not compensated (this only affects what those two buses send to device channels)
Changing an input's audio effects makes no audible differencePer-input effects do work: check whether "Enabled" is off (= bypassed); inputs have no limiter (a limiter cell written through the API is listed under "Other effects (kept as is)" and does nothing; only buses get a limiter); a second compressor in the same chain is not installed; EQ bands beyond 16 written through the API are not installed
Sound stays after cutting away / no sound after cutting inFirst the AFV master switch in the mixer header: off by default in a new show, and while it is off no input's "Follow video" has any effect. With it on, check that input's "Follow video": off = always audible, on = only on PGM
The headphones play Master; inputs sent to H can't be heardThe headphone output carries the "monitor source", Master in a new show: pick "Headphone bus" in the Listen menu (headphones icon on the Master strip) to hear what the inputs send to H; while something is soloed it always carries the soloed inputs
While soloing, headphones are ahead of the pictureThe solo monitor point defaults to before the alignment delay (low latency); to align with the picture choose "After the delay line" in Settings › Show Audio › Headphone monitor point, then "Apply and Restart Engine". With a compressor / limiter on Master the picture is delayed again by that much, and the soloed inputs, which skip Master's effects, stay early by that amount
Solo / PFL / AFL silent, the mixer header says "This device has no headphone channels"The output device has only 2 channels and Master uses them: turn on "Use the Master channels while monitoring" in Settings › Audio Devices (while soloing, the speakers / headphones play the soloed inputs; applies immediately), or pick a multichannel device and give the headphones a channel pair
No sound from Bus A / BGive Bus A / B a channel pair in Settings › Audio Devices (needs a multichannel device), then Apply and Restart Engine
Reminder "For 30 seconds the Master level has stayed below −50 dBFS (is the mic on?)"Check whether the microphone input is muted, its fader, whether it feeds Master, and whether "Follow video" keeps it out
"Audio device "…" unavailable (…); using the null device"Device unplugged or held exclusively by another app: reselect in Settings › Audio Devices; with the null device picture, recording and streaming keep their audio, only local playback is silent

9. Logs and diagnostics

  • Help › Export Diagnostics…: settings (without the API token), the last second of statistics, the show file with stream keys removed (the key field, user:pass@ in URLs and the values of secret-looking parameters are masked — parameter names in percent-encoded spellings such as pa%73s count too — and with the key field empty and the key written as the last segment of an RTMP URL, that segment is masked as well), the shortcut / MIDI tables and system information; with your consent also crash diagnostics and the last two hours of logs. It is saved where you choose in the save panel and selected in Finder afterwards; you can open and check it before sending it. Help › Show Diagnostics Folder selects ~/Library/Application Support/PlusMix/Diagnostics in Finder, which holds the crash / hang and other diagnostic records macOS hands over (crash-….json, hang-….json and so on; the latest 100 are kept), not the exported bundles. "Show Logs…" in the Stream / Recording Status window exports the last 10 minutes of this app's system log (the virtual camera extension included) to a log-….txt in this folder and opens it — the easiest way to read the streaming / recording logs.
  • Notices from the engine (recording, streaming, NDI® output, external displays, virtual camera and the like) also go to the system log; notices raised by the bottom bar itself (e.g. "No route takes part in recording…", "Transition in progress…") don't. The last 10 minutes (the full path /usr/bin/log works everywhere: a plain log is fine in Terminal, but in scripts or non-interactive zsh it hits zsh's own built-in of the same name and fails with "too many arguments"):
/usr/bin/log show --predicate 'process == "PlusMix"' --last 10m --style compact
  • One statistics line per second (stats.jsonl, fields in test standard §7 (repository: docs/testing/测试标准.md), Chinese): launch with --stats <file>, or read stats from GET /api/v1/state; the statistics window shows the same data. Attach it when reporting a problem.
  • Reproducing with the headless engine is often easier: switcher-headless run --show <show> --duration 60 --stats /tmp/stats.jsonl (Samples (repository: Samples/README.md), Chinese).

10. Known issues

Still present in this version and likely to be noticed (the full list is the product defect table in docs/KNOWN_ISSUES.md, Chinese):

SymptomWorkaround
RTMP / RTMPS to an untrusted server: a server that stuffs deeply nested data into its replies can crash PlusMix (HaishinKit, the third-party streaming library, parses those replies without limits). Without Adobe credentials in the URL (user:pass@) — the query-string method included — every reply is parsed by HaishinKit; with Adobe credentials only the first two rounds (asking whether authentication is needed, fetching the challenge) are parsed by PlusMix itself and are protected, while the third round and the connection after it still go through HaishinKitOnly stream to your own, trusted servers
The Streaming page's URL field: with the key field empty and the key written as the last segment of an RTMP URL, that segment is shown in clear (the bottom bar's ▴ tooltips, the diagnostics bundle and the API state already mask it)Put the key in the key field; don't keep the Streaming page open while sharing your screen
When the local API allows the local network, the token and the whole state travel as plain HTTP / WebSocket (no TLS): anyone who can see the traffic on the way can take the token (the Remote Control page shows a yellow warning)Only allow the local network on a network you trust; across networks use a tunnel (VPN / SSH forwarding)
