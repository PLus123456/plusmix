输出

每种输出在设置窗"本节目"那一组里有一页：输出总览、录制、ISO 分路、推流、外部显示、NDI® 发送、虚拟摄像头、多画面布局；菜单"输出"下面列着这几页，底栏的 ⚙ 打开对应的页（录制的 ⚙ 是"录制设置… / ISO 分路录制…"两项的小菜单，外部显示的 ⚙ 是路由菜单），底栏按钮的主体和 ▴ 是现场操作的快捷入口（概念 › 底栏按钮）。

每个输出有编号、名字、"应该在跑"的开关和自己的设置。每一节标题行写"种类 k · 输出 n"，右边是名字框（回车或离开输入框就改名）。运行中的帧数 / 码率 / 丢帧只在状态行、统计窗和 API 的 stats 里，不存进节目文件。

种类送什么开关怎么起
录制PGM，或某一路输入（ISO）底栏"录制"一起起停；▴ 单路停；快捷键 / API startRecord
推流PGM底栏"推流"、▴ 单路起停、推流页每段的开关；startStream
NDI® 发送PGM / PVW / 多画面 / 某一路输入NDI® 发送页的"发送"开关；setOutputEnabled
外部显示PGM / PVW / 多画面 / 某一路输入（Aux）底栏 / 工具条"外部显示"、监视器右键 › 全屏输出到；setOutputEnabled
虚拟摄像头PGM输出 › 虚拟摄像头 ▸ › 启用 / 停用虚拟摄像头输出；setOutputEnabled
多画面不单独送画面，只承载布局（见多画面）没有开关；要多画面画面就把 NDI® 发送 / 外部显示的来源选成"多画面"

0. 输出总览

设置 › 输出总览（菜单 输出 › 输出总览…）：节目里每个输出一行——种类、名字、来源、开 / 关、状态，最右"详情 ›"。点一行就跳到它的设置页、滚到那一节。录制的"开"= 正在录，推流的"开"= 应该在推（实际情况看状态）。状态和底栏、控制 API 读的是同一份统计。

1. 录制

ISO 分路

设置 › ISO 分路（底栏 ⚙ 录制 › ISO 分路录制…，或 输出 › ISO 分路录制…）：给每一路输入单独录一个文件。

  • 页顶："格式 H.264 · 18 Mb/s · .mov（同录制 1）"带"更改格式…"、目录带"更改目录…"——ISO 的格式和目录跟录制 1。改了录制 1，没在录的 ISO 路马上跟，在录的停了再跟（下一次开录生效）。
  • 表：行 = "PGM · 录制 1" + 每一路输入；列 = 录（勾选框）/ 名称 / 状态 / 时长 / 丢帧 / 目录。"时长"在录时写 hh:mm:ss（PGM 行 = 录制 1，输入行 = 它那一路 ISO），没在录写"—"。勾一路输入 = 给它加一个录制输出（来源 = 这一路的原始画面，文件名模板带 {output}）；取消 = 删掉那一路 ISO。 PGM 那一行取消 = 录制 1 不参与 = 只录 ISO。正在录的行锁着（停了以后才能改）。纯音频 / 图片输入默认收起，"显示全部输入（另有纯音频 / 图片 n 路）"展开。纯音频输入那一行名字下面写"纯音频：画面为黑"：勾上录出来的是黑画面 + 这一路的声音（和别的 ISO 一样：格式跟录制 1、默认 .mov，起止拍对齐，能直接拖进剪辑软件对轨）。
  • 与 PGM 同一拍起停、共用起点，所以各文件同一事件的时间差实测 0.0–0.2 ms（测试标准（仓库：docs/testing/测试标准.md） A4 要求 ≤ 1 帧）。
  • ISO 文件的音轨 = 该路推子后、AFV 之前的声音（切走了也照录）。
  • 30 fps 的输入录成 60 fps 节目时每帧重复一次，与 PGM 同一网格。
  • 每路输入最多 4 个分支（ISO / Aux 外部显示 / NDI® 输入源共用），用完会提示。
  • 录着的时候换这一路的来源（输入设置 › 来源）：ISO 跟着新来源接着录，文件不断、拍点连续；换源那一下重复几帧旧画面，新来源第一帧到了就换上。换到起不来的来源（文件不在、建不出来）或纯音频设备时这一路录成黑的；新来源能起来、但还没出画面（摄像头没插、NDI® 源还没上线）时这一路 ISO 录的是旧来源的最后一帧，直到新来源出第一帧；出过画面之后才断的，停在新来源的最后一帧，和同一来源中途断掉一样。录着的时候把这一路删掉不算换来源：这一路 ISO 停在删除的那一拍（实际多录约 3 拍），状态行提示"ISO 录制 n 停了：输入 m 删掉了（停在删除那一拍；再加同编号的输入不会接着录，要录再开一次）"（录像封好口时随即换成同一句后面接"——已封口：文件名，n 帧 / x s"，两句都在"显示日志…"导出的日志里），这一路 ISO 的录制开关自动关掉（ISO 页 / 底栏写"未开"）；新加的那一路不会自动接着录，要录再开一次。 ISO 的音轨跟着这一路的编号走：换源时新来源的声音接到哪个混音位置，音轨就跟到哪里，不会录到别的输入。
  • 页底写着录制目录、剩余空间和"还能录多久"（按所有录制输出码率之和估）。

磁盘保护

每秒看一次每路录制的剩余空间（外置盘 / 镜像也算对）：

情况行为
剩余低于 1 GB状态行提示"录制 n：磁盘剩余 x MB"
剩余低于下限（默认 200 MB；设置 › 高级 › 磁盘下限，或启动参数 --record-min-free-mb）只停这一路录制，提示"录制 n：磁盘剩余 x MB，低于下限 y MB"；推流、画面、别的录制不受影响。设了备用目录就改为切过去接着录，提示"录制 n：磁盘剩余 x MB，低于下限 y MB，已切到备用目录：文件名"
写满 / 写入失败（错误码是磁盘满，或失败那一刻剩余不到 64 MB，或卷被拔掉）这一路停并保留已写片段，提示"录制 n：磁盘满（…）"；设了备用录制目录（设置 › 高级，或 --record-fallback）就改为约 2 拍后在备用目录接着录，提示"录制 n：磁盘满，已切到备用目录：文件名"（录制器失败到被发现最多差 1 秒，这一段没录进任何文件）
录制器出错（编码器、格式这类，或空间充足时别的写入错误）只停这一路，提示"录制 n 失败：原因"；不切备用目录。这一路的开关仍开着、显示红色"起不来"，改设置不会自己重试：在底栏录制 ▴ 里点它（"只停这一路"）停掉，下一次开录时再一起开
  • 低于下限停下（或 ISO 那一路被删）的那一路封好口时，状态行换成同一句后面接"——已封口：文件名，n 帧 / x s"（例如"录制 2：磁盘剩余 150 MB，低于下限 200 MB——已封口：…"）。写满 / 写入失败 / 录制器出错的那一路，录制器已经先失败了，随后状态行是"录制 n 封口失败：notRecording"（已知问题，程序写法；已写的片段照留，看它前面那一句就知道为什么停）。
  • ISO 路切备用目录要再开一个画面分支（新文件约 2 拍后起录，旧的那个封口之前一直占着分支）：这一路输入的 4 个分支（ISO / Aux 外部显示 / 源是它的 NDI® 发送）都占着时不切，停这一路并提示"…；备用目录：这一路的画面分支满了（输入 n 每路最多 4 个 ISO / Aux），没有切，已停这一路"——不会悄悄改录 PGM。备用目录本身起不来时同样停这一路，提示"…；备用目录也起不来：…"。

测过的场景：录到 50 MB 的小镜像、两路 40 Mbps 同时写满（测试标准（仓库：docs/testing/测试标准.md） S7）。

2. 推流

设置 › 推流（底栏 ⚙ 推流，或 输出 › 推流设置…）：每个目的地一路输出，各自编码、各自重连。页顶"全部开始 / 全部停止"（停也先问），右边"推流状态…"打开推流 / 录制状态窗。

每个目的地一段，段名"推流 k"、副标题"输出 n"、名字框；段首一个"开始 / 停止"开关（没有地址不让开，关 = 先确认），下面一行状态："推流中 · 5.9 Mb/s · 丢 3 帧 · 重连 1 次"。

项说明
服务自定义（RTMP / RTMPS）、自定义（SRT）、微信视频号、抖音、哔哩哔哩、快手、YouTube、Facebook、Twitch。入口固定的服务（YouTube、Facebook、Twitch）选了就填好地址，推流码去平台后台拿；每场发地址的平台（视频号、抖音、快手、哔哩哔哩）不填，按说明去平台直播后台复制"推流地址 + 推流码"贴进来。节目文件里只存完整地址，重开时按地址认服务：只认得出入口固定的（YouTube、Facebook、Twitch）和哔哩哔哩，视频号 / 抖音 / 快手的目的地重开后显示成"自定义（RTMP / RTMPS）"（地址照旧，推流不受影响）

密钥RTMP 拼在地址后面作流名；SRT 没写 streamid 时补成 streamid=密钥
鉴权…见下面的推流鉴权
质量1080p（节目 ≥ 48 fps 时 6 Mb/s，否则 4.5 Mb/s；音频 AAC 160k）、720p（3 Mb/s；AAC 128k）、自定义。新目的地默认取不高于节目的那一档（最高 1080p，不放大）；手改了编码就显示"自定义"
编码详情…编码器、分辨率、码率、关键帧（按秒，新建时 2 s，旁边写"= n 帧"）、音频码率、重试间隔最长 n s（一直重试，鉴权失败除外）
与推流 1 相同第 2 个目的地起默认勾着：质量和编码跟着推流 1 改（地址、密钥、重试间隔不跟）；勾着时这两项灰掉
删除目的地开关开着时灰着（连接中 / 重连中也算；起不来 / 失败的那一路开着也能删）
  • 页底"合计上行约 n Mb/s（m 个目的地）"：每个目的地单独编码、各占一份上行，两个目的地就是两倍；上行带宽最好留出一倍余量。
  • 开关开着的那一段锁着（在推、连接中、重连中都算，只有"起不来"和"失败"的不锁）：服务、地址、密钥、鉴权、质量、编码详情、删除都改不了，写"正在推流：地址、密钥和编码停止后可改。"——一直连不上、要改地址或鉴权时，先把这一段的开关关掉。
  • 地址 / 密钥改完按回车或离开输入框才提交。
  • 起不来的那一段不锁：写"起不来：原因"（例如"起不来：没有地址"、"起不来：不认这种地址：foo://（只支持 rtmp:// rtmps:// srt://）"），给"重试"和"停用这一路"，下面红字"改好地址 / 密钥（回车或离开输入框）会自动重试；也可以先停用这一路。"状态行那句是"推流 n 起不来：没有地址"（n 是输出编号）。
  • 服务器拒绝鉴权停下的那一段同样不锁，但写"失败：鉴权失败（…）：…"，红字换成"这一路已停止、不再自己重连（服务器拒绝了鉴权）：改对地址 / 账号后点「重试」，光改设置不会自己重试；也可以先停用这一路。"——改好后要点"重试"，见推流鉴权。
  • 页底"添加目的地"一段：选服务（入口固定的直接填好地址，其余给一句去哪拿），填地址 / 密钥后点添加；节目里还没有目的地时点底栏"推流"主体也是打开这里、光标放在地址框。
  • 重连：断线后指数退避自动重连，一直重试不放弃（连不上也一样）；"重试间隔最长 n s"（默认 30 s）是两次尝试之间等待的上限，不是"超过就放弃"。重连后第一帧是关键帧。唯一的例外是服务器拒绝鉴权：被拒的那一次就停，不再重试（见推流鉴权）。
  • 多路推流互不影响：一路断网，其他路丢帧 0（E7）；断网 30 s 恢复后 10 次全部重连成功、≤ 15 s（E8）；带宽不够时的"网络丢帧"计数与真实丢帧差 ≤ 5%（E9）。这些都在本地 MediaMTX + 网络损伤下自动测。

底栏和工具条上的推流状态按最差的那一路汇总，在推时带时长：节目里只有一个目的地时写"● 推流 00:10:00"；有几个目的地时写"● 推流 00:10:00（2/3）"（在推的路数 / 目的地总数，只有一路在推也是"1/3"）；时长读统计（这一路本次推了多久，从开始推算起、断线重连期间也算），多路取最长的那一路。有路在重连、第 2 次起还没连上、起不来或失败时写"推流 · 1 路异常"（橙；起不来 / 失败的是深红），只开了一路时直接写它的状态（例如"推流 · 重连中（第 2 次）"、"推流 · 起不来"、被拒绝鉴权停下的"推流 · 失败"）。首次连接写"连接中"（第 2 次起"连接中（第 n 次）"），连上过之后断了才写"重连中（第 n 次）"，n 是真实的尝试次数。悬停提示逐路列"名字：状态"，起不来 / 失败的带原因，地址里的口令打码；有这种路时末尾一句"点一下：重试起不来的路，正常的路不受影响"（有失败的路时写"起不来 / 失败的路"）。开始时状态行提示"推流 n 连接中…"，真正推上了才提示"推流 n 已开始"。 ▴ 里每个目的地一项（点 = 只开 / 只停 / 只重试这一路），"推流状态…"打开推流 / 录制状态窗。每一项的悬停提示依次写：起不来的原因（"起不来：…"）或被拒绝鉴权停下的原因（"已停：鉴权失败（…）：…"）、这一路的地址（"地址：…"，user:pass@ 和像口令的参数值换成 <redacted>；密钥栏空着、密钥直接写在 RTMP 地址末段时末段也换成 <redacted>）、点了会做什么。 API stats.encoder[] 里推流的 state 是 idle / connecting / publishing / backoff / stopping / stopped / failed；起不来、被拒绝鉴权停下的那一路都报 failed。

推流 / 录制状态窗

一扇独立的窗（"推流 / 录制状态"），上面分"推流 / 录制"两页。入口：底栏推流 ▴ 的"推流状态…"、底栏录制 ▴ 末尾的"录制状态…"（菜单栏 输出 › 推流 ▸ / 录制 ▸ 就是这两份菜单）、推流页顶上的"推流状态…"、录制页顶上的"录制状态…"。从哪个入口开就停在哪一页，已经开着就叫到前面。

页每一路一行，列
推流名称 / 状态 / 码率 / 丢帧 / 重连（断了又连回来的次数）/ 时长 / 断线（连上之后掉线的次数）/ 最后错误
录制名称 / 状态 / 时长 / 码率 / 帧数 / 丢帧 / 剩余空间 / 最后错误
  • 数字全读统计（stats.encoder[]，与 API、状态行同一份），窗里不另算；没开的路状态写"未开"、码率和时长写"—"；重连中是橙字；起不来的写"起不来"、停住 / 失败的写"失败"（与底栏、推流页同字），都是红字。
  • 最后错误：这一路最近一次出错时推流 / 录制模块写下的那一行原文（下一次开始时清空），地址里的口令已打码。推流的几种：
    • 连不上：连接失败：<原因>，原因是一句中文概括，例如 连接失败：连接超时（服务器没回）（5 s 内没连上，或连上了服务器一直不说话）、连接失败：连接被拒（这个地址和端口上没有服务器在听）、连接失败：找不到主机（域名解析失败）、连接失败：SRT 连接超时（服务器没回）；服务器回了状态时是 连接失败：服务器拒绝连接：<状态码> <描述> 或 连接失败：发布被拒：<状态码> <描述>；开始推（publish）那一步服务器不回，同样等到 5 s 连接超时报 连接失败：连接超时（服务器没回）（连接超时管整个连接过程），3–5 s 之间才回成功的是 连接失败：发布：服务器 3000 ms 之后才回 NetStream.Publish.Start，这条连接作废、重连；Adobe 鉴权前两轮服务器的回复嵌套过深 / 元素过多是 连接失败：RTMP 协议错误：AMF0 嵌套过深（…元素过多），照常退避重试。底层库的原话只进系统日志（"显示日志…"导出的那份里有），这里只放概括；每次连接前建不出传输层时是 建传输层失败：<原因>（同样退避重试）；
    • 推上过、断了：断线：连接断开、断线：发送停滞（有数据要发、连续 5 s 一个字节都没发出去）、断线：发送失败：<原因>；
    • 起不来（地址不认、没有地址、这一路建不起来）：原因本身，例如 没有地址、不认这种地址：foo://（只支持 rtmp:// rtmps:// srt://）（状态行那句前面带"推流 n 起不来："）；
    • 服务器拒绝鉴权：鉴权失败（用户名或密码不对）：NetConnection.Connect.Rejected … reason=authfailed …（冒号后面是服务器回的原文，见推流鉴权）。
  • 下面"事件"：带时间的状态变化，新的在上，每条"名字 · 事件"——连接中 → 推流中 → 断开：<最后错误>（例如"断开：断线：连接断开"）→ 重连中（第 n 次）→ 重连上 / 已停止 / 起不来：原因 / 失败：原因（第一次看到这一路时它就已经起不来的，只写"起不来"）。由每秒一次的统计推出，一秒内来回的看不到； 窗口关着也照记，换节目 / 重起引擎时清空，最多留 500 条。
  • 底部"效果链延迟"一行：每条总线、装了效果的每一路各一项，例如"效果链延迟：Master 12.0 ms · Bus A 0.0 ms（压缩器实测 0.00 ms） · Bus B 0.0 ms · 耳机 0.0 ms · 输入 3 话筒 0.0 ms"——读统计里的 audio.effects，装着自写压缩器的那几条跟着它的实测值。
  • 再下面"视频延后 n ms"：只在画面为监听同步延后时出现（Master 开了压缩 / 限幅，见概念 › 音频），就是统计里的 video_delay_ms。
  • "显示日志…"：把最近 10 分钟本程序（含虚拟摄像头扩展）的系统日志导出成一份文本 log-年月日-时分秒.txt，放进诊断文件夹（~/Library/Application Support/PlusMix/Diagnostics）并打开，要几秒；推流 / 录制模块打的日志就在里面。也可以自己查系统日志，见 故障排查 › 日志与诊断。
  • 这扇窗在前时快捷键照常派发（直播中开着它盯着看，按空格照样切）。

推流鉴权

"鉴权…"按地址的协议弹不同的小表；这一段的开关开着时改不了（锁着），先关掉开关再改（起不来、或被服务器拒绝鉴权停下的那一路不锁，开着也能改）：

  • RTMP / RTMPS：小表"RTMP 鉴权（用户名 / 密码）"，最上面"写法"二选一：
    • Adobe（user:pass@）：Wowza、Nimble、FMS 和一部分要鉴权的 CDN 入口用（Adobe 鉴权，FMLE 兼容）。用户名和密码写进地址的 user:pass@ 一段，连接时按挑战应答算，不把密码明文发出去；地址框里显示成 rtmp://•••@host/app，"鉴权…"按钮旁写"鉴权：用户 xxx（密码已设）"（没填密码时写"（没有密码）"）。
    • 查询串（?user=&pass=）：MediaMTX、SRS、nginx-rtmp 这类自建服务器用，写成地址后面的 ?user=…&pass=…。下面多两格"用户名参数 / 密码参数"：默认是 MediaMTX 的 user / pass， SRS、nginx-rtmp 按服务器上鉴权回调的规矩改（只能用字母、数字和 - . _ ~，两个不能一样）。值在地址框里打码（?user=•••&pass=•••），按钮旁写"鉴权（查询串）：用户 xxx"。密码参数的名字不在打码名单里时（名单：user、pass、password、pwd、key、token、secret、passphrase、streamid、auth、response），表上提醒"参数名'…'不在打码名单里：地址框和日志里会显示明文"。 参数名记在本机：节目文件里只存整条地址；重新读地址时认 user / username / usr 与 pass / password / pwd / passwd，再加上这台 Mac 在表里存过的参数名（最近 8 对）——认写法、换写法时都按它们，换成 Adobe 写法时按认出的名字把那两个参数去掉。所以在另一台 Mac 上打开用了自定义参数名的节目，按钮旁会写"没有鉴权"、再打开小表停在 Adobe、框是空的（推流本身不受影响，地址照旧）：在表里选"查询串"、按原来的名字重填一次，这台 Mac 就记住了。
    • 两种写法互斥：保存一种时另一种的账号从地址里去掉；用户名留空再保存 = 两种都去掉（没有鉴权）。地址里别的参数原样留着。
    • 选错写法推不上：MediaMTX 收到 Adobe 写法时连接会成功、开始推的时候被服务器拒（NetStream.Publish.Unauthorized），按鉴权失败停下（见下）；SRS、nginx-rtmp 这类用鉴权回调拒绝的直接断开，照旧一直重试（见下）；要 Adobe 鉴权的服务器收到查询串写法，按"服务器要用户名和密码，地址里没写"停下。
    • "清除"只把用户名和密码框清空，点"保存"才改地址；没有鉴权时按钮旁写"没有鉴权"。
  • SRT：passphrase（加密口令），写进地址的 passphrase= 参数；只能用字母、数字和 - . _ ~，10–79 个字符（别的字符现在推不上），不合格直接报错不写。
  • 服务器拒绝鉴权（用户名 / 密码不对、写法选错、服务器要账号而地址里没写、要的鉴权方式不支持）：被拒的那一次就停，不按退避重试（密码不会自己变对）；第一次连接、断线后重连都一样。
    • 状态行一句"推流 n 鉴权失败（用户名或密码不对），已停止：在推流页改对后点底栏「推流」重试"；服务器要 Limelight（llnw）时是"推流 n 不再重连：鉴权失败（服务器要的鉴权方式不支持）：…"（这一版不支持，改密码没用）。
    • 底栏推流主体深红"推流 · 失败"（开着几路时"推流 · k 路异常"），悬停写"名字：失败 — 鉴权失败（…）：…"和"点一下：重试起不来 / 失败的路，正常的路不受影响"，▴ 里这一项悬停"已停：鉴权失败（…）：…"；推流页那一段写"失败：鉴权失败（…）：…"、不锁（红字见上面推流一节）。状态行的推流码率不算这一路（只有它开着时写"—"）。 状态窗里这一路状态写"失败"，事件"失败：鉴权失败（…）：…"，"最后错误"是同一句；API stats.encoder[] 这一路 state = failed、attempt = 0、last_error 同上。
    • 原因看开头：鉴权失败（用户名或密码不对）（Adobe 写法服务器回 authfailed / nosuchuser；查询串写法被拒，原文是 NetStream.Publish.Unauthorized）、 鉴权失败（服务器要用户名和密码，地址里没写）（这时状态行那句也写"用户名或密码不对"）、鉴权失败（服务器要的鉴权方式不支持）；冒号后面是服务器回的原文，不带密码（只有地址里写了 Adobe 账号、服务器却要 Limelight 时，冒号后面是一句"服务器要 Limelight（authmod=llnw）"）。
    • 改对之后点底栏推流主体（或推流页那一段的"重试"）：停掉这一路、按新设置重新起；开关不用关。改地址 / 账号本身不会自动重试这一种。
    • 查询串写法推 MediaMTX：地址只写一段路径（如 rtmp://127.0.0.1:1935/s1）、密钥留空——MediaMTX 惯用的写法——第一次就停；填了密钥、或地址路径有两段（如 rtmp://host/live/s1）时，每次连接先多等约 3 s，加上 MediaMTX 故意晚 0–4 s 才回拒绝，常常超过 5 s 的连接超时：那一次按"连不上"退避重试，平均两次左右才认出来停下。
    • 认不出的拒绝照旧一直重试（"连接中（第 n 次）"）：服务器拒绝时直接断开、不回原因的（例如 SRS、nginx-rtmp 用鉴权回调拒绝时），以及 SRT 的 passphrase 和服务器上的不一样。原因去服务器那边的日志里看。

mediamtx scripts/mediamtx.yml

在仓库根目录起本地服务器（它会把收到的流录进当前目录下的 mediamtx-recordings/）。推流地址填 rtmp://127.0.0.1:1935/s1、密钥留空（这份配置只开了 s1 / s2 / s3 和 SRT 的 srt1 四个路径；推到别的路径会一直"连接中"），然后看：

SRT 用 srt://127.0.0.1:8890?streamid=publish:srt1。RTMP 与 SRT 在本项目里端到端测过；RTMPS 走同一条路，只是加了 TLS（示例 › 直播（仓库：Samples/README.md））。

3. NDI® 发送

设置 › NDI® 发送（输出 › NDI® 发送设置…，或底栏 ⚙ 外部显示 › NDI® 发送设置…）：每路发送一个输出，源名就是输出的名字，网络上显示为 机器名 (输出名)。（NDI® is a registered trademark of Vizrt NDI AB.）

项说明
来源PGM / PVW / 多画面 / 某一路输入（Aux，原始画面：抠像 / 裁切 / 变换不生效）。PVW / 多画面按需多出一路画面，开头可能缺一两帧
分组NDI® 分组名（逗号分隔），空 = 默认组 public。接收端按分组过滤
转换NV12 → UYVY 的转换用 GPU / CPU / 自动（自动 = 定期比一次，哪个省用哪个）；只对 NV12 的画面起作用（见下）
音频PGM / PVW / 多画面送 Master；某路输入送该路推子后的声音
发送开关：关掉 = 停发，设置留着
  • 页底"添加 NDI 发送"：填名字、分组、转换、来源后点添加；新加的一路一建就开着、马上开始发。
  • 改名 / 改来源 / 改分组（"应用名字 / 分组"）会重建发送端（接收方要重新选源），转换方式随时切。
  • 送出去的像素格式跟来源走：PGM / PVW / 多画面和 NV12 的输入（摄像头、不带 alpha 的视频文件这类）转成 UYVY 送；BGRA / UYVY 的输入（图片、带 alpha 的视频文件、屏幕 / 窗口、NDI® 输入、DeckLink）不转换、按它自己的尺寸直接送。 BGRA 一律按不透明（BGRX）送，下游拿不到 alpha：带透明的图片 / 视频透明处到下游是黑的，半透明的边偏暗。要叠字幕，在 PlusMix 里叠好再送 PGM。比节目大的 NV12 输入（例如 4K 的视频文件进 1080p 节目；摄像头一般会协商到节目尺寸）只送左上角节目大小的那一块（已知问题）。
  • SDK 不在（编译时没探测到 NDI SDK for Apple）：输出能加、能开，但不会真的发出去；状态显示"不可用：没有 NDI SDK"，API stats.encoder[] 里这一项 state = "unavailable"。
  • SDK 在但起不来（初始化 / 建实例失败）：state = "failed"，状态行有原因；改设置后会重试。
  • 在发、但连续 10 帧送不出去（转换失败、像素格式送不了这类）也报 failed，原因在 API stats.encoder[] 这一项的 last_error（例如"NDI 送不了像素格式 '…'（只认 NV12 / UYVY / BGRA），连续 10 帧没送出"）；送出去一帧就回到在发。这时：
    • NDI® 发送页的状态写"失败：<原因>"（就是 last_error 那一句；没有原因时才写"起不来：有 NDI SDK，但初始化 / 建发送实例失败（看日志）"）；
    • 状态行提示一句"NDI 发送 n 出错：<原因>"（没有原因时"NDI 发送 n 出错（原因见输出设置的 NDI 页）"），同一路 60 秒内只提示一次（这一路停掉再开会重新算），在失败和在发之间来回翻不刷屏；
    • 翻成失败的那一刻也写进系统日志（推流 / 录制状态窗"显示日志…"导出的那份里有）。
  • stats.encoder[] 的 connections 是当前接收方数，bitrate 是按节目尺寸的 UYVY 算的原始码率（1080p60 约 2 Gb/s，这是正常的；直送 BGRA 或小尺寸输入时也写这个数）。

4. 外部显示（第二块显示器）

一路外部显示 = 一块显示器上的无边框全屏窗口。入口：

  • 底栏"外部显示"：⚙ = 路由菜单；主体 = 全部开 / 关。工具条正中的"外部显示▾"、菜单 输出 › 外部显示 ▸ / 打开（关闭）全部外部显示 是同一套。
  • 右键 PGM / PVW 监视器 › 全屏输出到 ▸：这块屏改成显示这个监视器（概念 › 主窗口）。
  • 设置 › 外部显示（输出 › 外部显示设置…）。

路由菜单：每块屏一段单选（PGM / PVW / 多画面 / 输入 n），打勾 = 这块屏正在显示的源；这块屏已经配过时最上面一行是"关闭"（这块屏不出画面、配置留着），关着的那一路标"（已关）"。点一个源：这块屏已有一路就换源并打开、同屏别的路关掉，没有就加一路。往下是"删除 n …（状态）"和"关闭全部外部显示"，最后一段是"外部显示设置… / NDI® 发送设置…"。

主体：有开着的 → 全部关（配置留着）；都关着 → 按原来的配置全部开；一路都没配 → 在第一块非主屏（主屏 = PlusMix 主窗口所在的那块）上全屏显示 PGM；没有第二块屏 → 弹路由菜单。

设置页最上面是"每块屏送什么"：每块屏一个单选，与路由菜单是同一份设置。下面是每一路的细项：名字、启用、显示器、来源、显示器不在时退回主屏、状态，最后是"删除这一路"按钮——它删掉这一路和它的设置（同路由菜单的"删除 n …"，不问）；只想暂时不出画面，关掉这一节顶上的"启用"、用路由菜单里这块屏的"关闭"或底栏主体。

  • 来源：PGM / PVW / 多画面 / 某一路输入（Aux，全分辨率原始画面；那一路在 输入设置 › 来源 换了来源时跟着新来源走）。
  • 显示器不在时：默认黑着等它回来、不动主屏；"显示器不在时退回主屏"会在主屏全屏（盖住操作界面），只在明确要的时候开。设置 › 常规 › 外部显示在主屏上不盖住主界面 可以让主屏上的外部显示窗垫在主界面下面。
  • 画面由显示器自己的刷新节拍取最新帧，拖动主窗口、进出全屏都不影响渲染线程（丢帧计数不增）。在外部显示窗口里按 Esc = 关闭这一路（同路由菜单的"关闭"：窗口收起，显示器 / 来源配置留着，再点源按原配置打开）。
  • 节目文件保存显示器 ID 和来源，重新打开时恢复；显示器 ID 重启后可能变，换了就重选一次。

5. 虚拟摄像头

设置 › 虚拟摄像头，或菜单 输出 › 虚拟摄像头 ▸：让 FaceTime、QuickTime、浏览器会议等把 PlusMix 当成一台摄像头。送的是 PGM（不可选来源），与录制 / 推流 / NDI® 拿的是同一块节目帧。

安装（一次）：

  1. 用带 Team ID 的签名构建（DEVELOPMENT_TEAM=<TeamID> make gen build-app），把 PlusMix.app 放进 /Applications 再启动——系统扩展只能从 /Applications 里的 App 激活。
  2. 设置 › 虚拟摄像头 › 安装…（或 输出 › 虚拟摄像头 › 安装 / 激活扩展…），然后到 系统设置 › 通用 › 登录项与扩展（旧版本在"隐私与安全性"）里允许。"检查"（菜单里"查询扩展状态"）看当前状态。
  3. 打开"开启虚拟摄像头"（或 输出 › 虚拟摄像头 › 启用 / 停用虚拟摄像头输出）。在 FaceTime / QuickTime 新建影片录制里选 "PlusMix" 摄像头。
  • 开发构建（没有 Team ID、ad-hoc 签名）激活会失败，状态显示"系统不允许安装：需要正式签名的版本，并从"应用程序"文件夹运行"，App 不崩。
  • 输出开着但扩展没连上：状态"找不到虚拟摄像头设备（扩展未安装 / 未激活）；已丢 n 帧"，每秒重试；连上后自动发。关掉输出后对方看到占位画面（深灰 + 移动白条）。
  • 帧率跟节目，1080p NV12；从 PGM 到对方进程 ≤ 3 帧是设计目标（签名机器上验证）。

6. 多画面

设置 › 多画面布局（底栏 ⚙ 多画面，或 输出 › 多画面布局…）；底栏"多画面"主体 / 窗口 › 多画面窗口 开关独立窗口，可拖到任何屏、全屏。

项说明
预设PVW / PGM + 按路数自动（默认：上 PVW / PGM，下半按路数 4×2 / 6×3 / 8×4）、PVW / PGM + 4×2、PVW / PGM + 2×2、3×3、4×4
格子用预设时可以"从当前预设转成自定义"（抄出预设每一格的位置）或"添加格子"；有自定义格子时逐格改：来源（PGM / PVW / 输入 n）+ x / y / 宽 / 高（按画面比例 0–1，超出画面的部分裁掉）+ 删除，末尾"添加格子 / 清掉自定义格子（回到预设）"。自定义格子非空时预设不起作用
安全框PGM / PVW 格画 EBU R95 动作安全 3.5% / 字幕安全 5%
电平表输入格画该路的表，PGM 格 = Master、PVW 格 = 当前 PVW 那一路；读数就是状态行 / API 那一份
  • 每格有 tally 边框（红 PGM / 绿 PVW）和名字标签；纯音频输入的格子画名字 + 电平表。
  • 布局存在节目文件里（第一个多画面输出的设置），对多画面窗口、缩略图条、外部显示 / NDI® 的"多画面"来源都生效。
  • 节目里的"多画面"输出只用来承载布局：页面上没有开关，新建时是关着的，保持关着就行。NDI® 发送 / 外部显示的来源选"多画面"时渲染器自己会出多画面画面，不看这个开关（用 API setOutputEnabled 打开它，只会让渲染器每帧多转一份没人用的多画面画面）。
