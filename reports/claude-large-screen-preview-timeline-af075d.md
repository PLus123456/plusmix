## 4. 对契约的疑问

1. **舞台放在 `MixerState` 里还是旁边。** 方案草案是 `MixerState.stage`（可空，空 = 行为不变）。编排数据（屏幕、分区、预设、时间线）体积大、很少变，运行状态逐拍变；放一起最简单，但每条命令的状态拷贝和相等比较会带上它们。036 要给出结论（数组是写时复制，未改动时比较走同一存储的快路径，量一下再定）。
2. **时间线走带放进 `advance`** 意味着 `advance` 不再只推进度，还会"自己发命令"。同一拍里"走带产生的命令"和"外面进来的命令"谁先谁后、回执怎么给、命令日志里怎么显示，038 要写清楚。
3. **`OutputSource` 加 `.stage(raster:)`** 是给节目文件里的枚举加 case：老版本程序读用了它的新节目文件会解码失败。以前加命令 case 没有这个问题（命令不进节目文件）。要用户定一次：容忍（配了大屏的节目老程序打不开），还是升 `schemaVersion`。
4. **输入上限 16**（提案 032）对放片多的演出是硬限制。方案用"播放器输入"绕开，不动上限；如果用户想直接提高上限，要回头看 032 当初的原因（兼容层按编号分配）。
5. **快捷键表加"面板范围"**（039）会改 `HotkeyTable` 的文件格式，用户已有的 hotkeys.json 要能照读。
6. 后续方案 §3.5 的多画布建议并入舞台（一个输出口 = 一块画布），V13 改名 V17。要用户同意才改后续方案。

7. **幻灯片列表输入**（提案 040，原来写的是播放器输入）：`InputSource` 加一种，带页列表与分段；PDF 页要在 macOS 27 上先写探针（渲染成位图的尺寸、色彩、耗时，铁律 10）。当前页号是运行状态，要进快照；它算不算"节目内容"（存不存进节目文件）要定。
8. **时间线分段**放在 `Timeline.sections`，还是做成多条时间线，038 要定；方案草案是前者。

第三版（一个输出）带来的，都归提案 036：

9. **`program` / `preview` 两个编号在配了大屏之后的含义。** 方案草案是"最近一次切上屏 / 选进预监的那一路"，兼容层的当前 / 预监输入、API 的字段照读它。真实的画面由两份墙面状态（节目、预监）决定。
10. **对调。** `completeTransition` 现在是 `swap(&s.program, &s.preview)`；配了大屏时对调的是两份墙面状态。T-bar 拉回 0 取消、转场进行中拒收命令的口径要跟着写清。021 的"切上 PGM 时从头播"要从"新 PGM 那一路"改成"新上屏的那几路"。
11. **音频跟随视频。** `TransitionEvent` / `AudioControlEvent` 现在带一对输入（from / to）；多个分区同时换时是一组。音频侧（含 C 热路径的命令）怎么表达要和 W1-D 的实现对一遍。
12. **Tally。** `MixerState.tally(ofInput:)` 是契约里的函数，要从"编号相等"改成"在当前布局的分区里"。
13. **改屏幕 = 改画布尺寸 = 换节目格式。** `setStage` 改了屏幕时要不要像换节目格式一样重建渲染（`loadShow` 现在不换格式，提案 034）；方案写的是"开演前做"。
14. 上面第 3 条的枚举 case 现在叫 `.raster(number:)`；第 6 条作废：第三版不把后续方案 §3.5 的多画布并进来，"直播和大屏放不同的画面"留给以后的"第二路节目"。

## 5. 下一个会话需要知道的坑

- **调音台是 SwiftUI（`MixerView`），条子高度现在是写死的**：推子 `.frame(height: 170)`、收起的组条 `.frame(width: 20, height: 300)`、中间的 `Divider().frame(height: 300)`。挪到下边一行后高度要跟着行高走（200–600），这三处都要改成按可用高度算；最小窗口时行高只有 200，要有紧凑条子。
- **`mixerPanel.widthAnchor ≥ 340` 是硬约束**，竖屏右边一栏在最小窗口只有 346，刚好够；再窄要让调音台横向翻页（它已经有输入组的横向滚动）。
- **用户说的"所见即所得"= 方案里的"直出"**。他对"预监后 TAKE"这个说法不熟，跟他说话用"先看一眼再变 / 立刻变"。

- **监看区的"最小高"不是画面决定的，是转场列决定的。** `monitorsMinimumHeight = max(300, transitionPanel.fittingSize.height)`，W5-A 时约 409。窗口窄时贴合高（最小窗口 196）远小于它，监看下面一定会空出一截。别试图把上半区压到贴合高，转场列会被压扁（V-32 那类问题）。
- **输入条高度 197 被用例钉着。** `MainWindowLayoutTests` 与 `InputStripTests` 里有按 197 / 195 写的断言，W6-A 要改口径（初始高改成算出来的），不是改阈值。
- **竖屏缩略图被钳在 16:9 的框里**（`InputCellView.thumbnailHeight` 的 `min(width * 9 / 16, …)`），是 W5-H 有意做的（自定义多画面格子再高也只左右留边）。竖屏排布要改它，注意别把自定义格子的情况改坏。
- **缩略图来自多画面纹理的格子**，不是输入自己的画面。竖屏画布下格子是竖的、横的机位画面在里面上下留边；想让缩略图显示信号源本来的比例要动多画面布局，不是 App 能单独做的。
- **外部显示有两条路**：PGM / PVW / 多画面走渲染器的纹理，某一路输入直出走 `AuxInputPresenter`（自己的着色器，1:1 时逐值）。舞台输出口属于前一种，逐值与否要探针确认。
- **示意页是 artifact 的源文件**：没有 `<!doctype>` / `<html>` / `<body>`（发布时套壳），本地直接打开也能看。改了要重新发布到同一个链接（发布前先 read 线上版）。本地预览没有套壳里那条 `[hidden]{display:none!important}`，页面自己的 `display` 规则会盖掉 `hidden` 属性，所以页面里自己写了一条。
- **HiRender 的"屏幕"在两代手册里不是一个意思**：4.x 的屏幕 = 一个显卡输出口，映射靠"切片"；5.x 的屏幕仍是真实输出口，但多了"表面"（在输出口上画的矩形，在舞台区域另有一份位置）。本方案的"屏幕"对应它 5.x 的表面、"输出口"对应它 5.x 的屏幕。跟用户或那位老师对用词时先问清是哪一代。
- **用户的原话里"时间线"可能指两种东西**（HiRender 的节目管理表，或轨道上摆素材块的时间轴线），开第三层之前要先问清（方案 Q4）。
- **本机常数表**（示意页脚注也有）：工具条一行 52、底栏 58、输入条初始 197、转场列宽 150、调音台 340、监看标题条 26、输入格"中"档 200 宽、格子含按钮高 153、输入条头行 30。
- **最大的坑：这位用户的"大屏"和"导播"是同一个输出。** v0.2 按"直播一路、大屏一路"设计，第二层整节方向错了，是 Q9 的大白话解释才暴露出来的。跟他确认模型时用他的场景讲（20.5:9 的墙、主视觉、耳屏、采集卡进来的 PPT），不要用"舞台 / 直播 PGM"这类抽象词。他嘴里的"节目"是 HiRender 的节目（= 画面预设），"布局"是他自己的词，"屏幕那一页"= 大屏面板。
- **`HotkeyTable.default` 已经占掉的键**：数字 = 选进 PVW，⇧ 数字 = 直切 PGM，空格 = Cut，回车 = 执行当前槽，F = FTB，⌥1–⌥4 = 转场 1–4，⌃1–⌃4 = 叠加 1–4。新键位先对这张表。
- **合成里写死整幅的地方**：`CompositorPasses.encodeProgram` 的画底和 `encodeTransition` 的每个分支都是 `dest: full`；Wipe 遮罩在着色器里按屏幕坐标算（`wipeAlpha(in.position.xy, u)`），在分区里做 Wipe 要改着色器；Zoom 是 `full.scaled(progress)`。
- **本地看示意页**：内置浏览器打开 file:// 只给静态快照，脚本不跑。要点页面就起一个本地服务，响应头要带 `charset=utf-8`（页面自己没有 `<meta charset>`，发布时外壳给），量手机宽度要临时注入 viewport meta。`.claude/launch.json` 不在 .gitignore 里，用完删掉。
- **中间那一列（`TransitionPanelView`）的组成和高度**：一个竖的 NSStackView，上下内边距 8；Cut 24；转场 1–4 各 24（间 4，之后 8）；FTB 24（之后 8）；"Overlay"标题约 14（之后 2）+ 一行 20（之后 8）；"T-bar"标题约 14（之后 2）、当前槽 20、时长分段 20、T-bar 28（各间 4）；空白（吃多余高度）；时钟 56（之前 8）。加起来 392；用例只保证 ≤ 409。分档时用 `fittingSize` 量，别抄这几个数。
- **可用高度 = 窗口高 − 110**（工具条一行 52 + 底栏 58）：1100×720 是 610，不是 662。手算过一次算错，方案里的表一律以示意页的算法输出为准。
- **示意页里宽度遇 .5 往下取**（472.5 → 472），和实拍一致；方案 §2.3 的 300×532 因此改成 299×532。
- **起独立会话的做法**（第一次这样用）：`start_session`，`model: claude-opus-5-5`、`effort: max`、`source_branch` 指到设计分支（方案和 prompt 没进 main，默认会从 main 切）。应用给的分支名带前后缀（`claude/w6-app-layout-f772d1`），让它自己建别名 `w6-app-layout`。它每次挂后台任务都会结束一轮、发一条"还在跑"的便条，不是做完了；做完的便条里有提交号。后续交代用 `SendMessage` 发到它的会话 id。
- **显示类用例的对照要在同一时刻做**：W6-A 说 ThumbnailRate 单独跑能过，我半小时后单独跑是红的（屏幕上的窗口变了）。判"环境红"要在同样条件下把改动前后挨着跑，别拿不同时刻的结果比。
- **内置安全检查会拦 `rm -rf "$变量/..."`**：变量可能为空。别绕，用不存在的新文件名（xcresult 路径带时间）或 `git worktree remove`。
