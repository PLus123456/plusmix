# 输入到达相位穿过拍点边界时的"重复 + 丢弃"串（V4 设计外）

归属会话 / 分支：W1-B / `w1-core`（引擎挑帧：`Engine.programClock` 里 `slot.latest(atOrBefore: ideal)`）。修法若要每路一个视频延迟 / 到达余量，`InputSettings` 没有这个字段（只有 `audio.delayMs`），要走 docs/contract-changes/ 提案。
发现于：G2 / `scenarios/m0.json` + `scenarios/m0-show.json` / 提交 `0bb31fe` 之后的 headless（冒烟 45 s 与 `make gate2` 10 分钟）

## 现象

V4（输入帧重复 / 丢弃率）。与节目时钟有相对漂移的路——3、4 号 59.94 fps、5 号 60 fps +100 ppm、6 号 60 fps −100 ppm——每当该路帧的到达时刻相位穿过拍点边界，就出现一串成对的"重复 + 丢弃"，而不是设计内的单个重复（59.94 → 60 每 1000 拍重复 1 次）或单个丢弃（+100 ppm 每 10000 拍丢 1 次）。

数值（`make gate2` 10 分钟、release、机器空闲，T = 35940 拍；stats.jsonl 帧槽计数，reports/G2-run-10min.md 的 V4 明细一）：

| 输入 | 真实帧率 | dup 累计 | 设计内 dup 期望 | drop 累计 | 设计内 drop 期望 | 设计外（精确核算） | StatsSummary 设计外 |
|---|---|---|---|---|---|---|---|
| 3 | 59.9401 | 58 | 35.9 | 22 | 0 | 42 | 0.061% |
| 4 | 59.9401 | 59 | 35.9 | 23 | 0 | 44 | 0.064% |
| 5 | 60.0060（+100 ppm） | 26 | 0 | 30 | 3.6 | 50 | 0.084% |
| 6 | 59.9940（−100 ppm） | 33 | 3.6 | 29 | 0 | 56 | 0.081% |
| 1、2、7、8（30 fps ×2、60 fps 抖动 ±3 ms、60 fps） | — | 17970 / 17970 / 0 / 0 | 17970 / 17970 / 0 / 0 | 0 | 0 | 0 | 0 |

四路合计设计外 192 帧（0.53% 的拍）；单路最差 0.084%，都超必须档 0.05%。每次穿越的样子（stats.jsonl 逐秒）：59.94 的路每 1000 拍一次穿越，每次多 ~1 对；±100 ppm 的路每 10000 拍一次穿越，每次 ~15 对（相位每帧只走 1.67 µs，在到达抖动带里停留 ~30 帧）。
frameprobe 读录制文件（只有在播的那路，明细二）：ID 2 在播 5372 帧重复 10 / 丢 5（设计内 5.4 / 0，设计外 7）、ID 5 在播 3600 帧重复 7 / 丢 6（设计内 0.4 / 0，设计外 10），同样超 0.05%。
45 s 冒烟（debug 构建）：输入 3 在 3 次穿越里 dup 4 / drop 1（设计内 3 / 0）；提前量为 0 时（帧 pts 正好在拍点）输入 3 两次穿越 dup 7 / drop 5，输入 5 一次穿越 dup 8 / drop 9。
阈值：设计外 ≤ 0.05%（测试标准 §4 必须档）；G2 通过标准要求设计外 0。

## 复现步骤

1. `make gate2`（或 `.build/release/switcher-headless run --show scenarios/m0-show.json --script scenarios/m0.json --duration 600 --stats s.jsonl --record o.mov --audio-device null`）。
2. 看 stats.jsonl 里 `per_input.3/4/5/6` 的 dup / drop 何时跳变：每次跳变是一串连续拍，间隔 = 相位周期（59.94：1000 拍 ≈ 16.7 s；±100 ppm：10000 拍 ≈ 167 s）。
3. 想放大：`--input-lead-ms 0`（帧 pts 恰在拍点，所有 60 fps 的路都贴着边界）。

## 严重级

S2：V4 必须档不过；画面上每次穿越多一到几次 16 ms 的抖动（重复一帧接着跳一帧）。

## 猜测原因与建议

`latest(atOrBefore: t_n)` 按 pts 判"合格"、按"已经 push 进槽"判"可用"。当某帧的 pts 落在拍点附近时，它在第 n 拍是否可见取决于到达时刻的抖动（合成源：唤醒 + 画帧；真设备：传输抖动）：晚到一点 → 第 n 拍重复上一帧（dup），第 n+1 拍它和下一帧一起在槽里 → 取最新、它被跳过（drop）。相位每穿越一次边界，处在到达抖动带内的那些帧都在赌（带宽 / 相位步进：59.94 每帧走 16.7 µs，±100 ppm 每帧只走 1.67 µs，所以 ±100 ppm 的每次穿越更长）。

W1-B 的 V4 测试（`testV4_5994Into60_oneReusePer1000Ticks`、`testV4_60fpsPlus100ppmInto60_oneDropPer10000Ticks`）用的生产者到达时刻没有抖动，所以量不到。

建议：合格与否只用确定量。每路一个到达余量 / 延迟 L_i（真设备 = 采集延迟，合成源 = 唤醒 + 画帧上限），取 `pts ≤ t_n − L_i` 的最新帧；只要 L_i ≥ 实际到达延迟 + 抖动，"合格"的帧一定已经在槽里，不再和到达赛跑。代价是每路多 L_i 的延迟，设计方案 §3.7 的"输入帧槽 1–2 帧"预算里本来就有这一项。L_i 放哪（`InputSettings` 加字段 / 引擎按 ingressTime − pts 自估）请 W1-B 定，加字段走提案。
