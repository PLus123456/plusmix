# W4-A → 检查点（G5）安排：进程 CPU "60%" 为什么不分到多核——数据说明已经分了、没有一个核在受累；要探查的是线程落在哪类核上、极限负载下谁先满

归属会话 / 分支：检查点定（候选：W1-B 引擎线程模型 / QoS，W2-D NDI SDK 线程，W4-A 报告口径已做）
发现于：W4-A 8 小时 soak（2026-09-28）之后用户提问："为什么不分开到多核呢？一核有难 n 核围观吗？……S3 意义不大，但还是要探查多核心的途径，到检查节点再往下安排"
严重级：S3（探查项；用户定 S3 不阻塞）

## 1. 先把口径说清

- `Stats.cpu_pct`（§7）= 进程**所有线程** CPU 时间之和 / 墙钟 × 100，**100 = 一个核**。8 小时的 60.1% = 进程合计 0.6 个核 = 18 核机器的 3.3%。它不是"某个核在 60%"。
- 报告从现在起把它写成"合计 N 个核"，并列**按线程**（`threads.log`）和**按核**（powermetrics）两张表（`scripts/soak/soak_report.py` 已加；8 小时报告已重出）。

## 2. 数据：已经分到多核，没有一个核在受累

**按线程**（8 分钟对照 `.build/soak/tcpu/`，同负载、无摄像头；每分钟快照之间的占核 %）：

| 线程 | 每分钟均值 | 峰值 |
|---|---|---|
| `ndis:async`（NDI SDK 压缩 / 发送） | 18.7 | **20.1** |
| 无名线程 × 11（VideoToolbox / AVFoundation / HaishinKit / GCD）合计 | 15.6 | 16.4（单线程最高 6.2） |
| `ndis:lowQ`（NDI SDK 的低带宽第二路） | 6.2 | 6.5 |
| 其余约 30 条（编码器交帧、推流音频、AAC、文件解码、时钟、音频、合成源……） | 各 ≤ 1.3 | 各 ≤ 1.3 |

最重的一条线程峰值也只是一个核的 20%；进程约 60 条线程由系统摊到各核。

**按核**（8 小时 powermetrics，每 4 样取 1；整机口径、含 MediaMTX / powermetrics 自己 / WindowServer 等；忙 = 1 − idle − down）：

| 簇（powermetrics 名 / `sysctl hw.perflevelN.name`） | 核数 | 平均频率 | 断电时间 | 每核忙时比均值 |
|---|---|---|---|---|
| S-Cluster / perflevel0 "Super" | 6 | 3.2 GHz | 0 | 26.1 / 23.4 / 17.6 / 11.9 / 8.8 / 4.6% |
| P0-Cluster / perflevel1 "Performance" | 6 | 1.3 GHz（底频） | 38% | 10.3 / 7.5 / 5.4 / 3.7 / 2.6 / 1.9% |
| P1-Cluster / perflevel1 "Performance" | 6 | 1.3 GHz（底频） | 38% | 9.7 / 7.4 / 5.3 / 3.7 / 2.6 / 2.0% |

整机 8 小时合计忙碌 **1.55 个核**（我们的进程 0.6 + 其它）；**任一时刻最忙的那个核均值 26%、p95 27%**。
结论：没有"一核有难"。调度器把这点负载集中在 6 个不断电的 Super 核上，12 个 Performance 核大部分时间在底频睡觉——这是 macOS 的省电放置，不是我们线程模型的限制。

（第一次算的时候用 1 − idle 忘了减断电时间，把 Performance 核算成了"忙 40%"，perfjudge 现在减 `down_ratio`，有用例。）

## 3. 那 cpu_pct 为什么看起来"高"

它是**时间**口径：同样的活放在 3.2 GHz 的 Super 核和 1.3 GHz 底频的 Performance 核上，花的时间差两倍多；线程去哪个核由 QoS 决定，
默认 QoS 的线程（NDI SDK 的 `ndis:*`、GCD 工作线程）不会被抬去高频核。所以这个数和"用了多少算力"之间隔着频率和放置两层，要拆就得看线程的 QoS / 优先级和它落在哪个簇。
`threads.log` 现在每行带 `pri=` / `policy=`（`scripts/soak/thread-cpu.swift`），够第 4 节第 1 条用。

## 4. 探查项（到检查点再安排；建议顺序）

1. **线程 QoS / 优先级清单**（一次性，半小时；归 W1-B）：把 `threads.log` 里每条线程的 `pri=` / `policy=` 与设计方案 §3 的线程表对一遍——
   实时线程（渲染、program-clock、音频）应是 policy 2 / pri > 80；`ndis:*`、HaishinKit、VideoToolbox 工作线程是默认 31。看有没有本该实时的线程掉在分时里、或者不该高的线程占了实时。
2. **线程落在哪个簇**（半天；归 W2-D + W1-B）：`sudo powermetrics --samplers tasks --show-process-qos -i 1000` 看本进程各 QoS 档的 CPU ms，对照按核表；
   写清"轻负载时活在 Super 核、Performance 核睡"是否成立，以及要不要给某些线程指定 QoS（比如 NDI 发送线程抬到 userInitiated 换更低的发送延迟——受益的是 L2 / L3 延迟，不是 S3）。
3. **极限负载下谁先满**（关键，一天；归检查点安排，要 4K 场景）：E1 那条"故意把编码器压到极限（4K + 3 路）"加上 `threads.log`，看第一个接近 100% 一个核的线程是谁。
   现在单线程峰值 20%（`ndis:async`）离满还远，但 4K NDI 发送的 SDK 压缩是单线程的、4 倍像素可能先撞到它；渲染线程 V1 1.9 ms @1080p，4K 约 ×4 也还在 16.7 ms 内。这才是"一核有难"的真正测试。
4. **报告口径**（W4-A 已做）：cpu_pct 写成"合计 N 个核"，加按线程 / 按核表；基线里存按线程表，退步看 `ndis:*` 之外的部分（W2-D 单子里的建议 (a)）。

## 5. 现在不建议做的

- 把 NDI 的 NV12 → UYVY 转换强制走 GPU：省 1 pt，且 GPU 8 小时都在最低频。
- 为了让 S3 的数字好看去调线程 QoS：数字会变（换到高频核时间变短），活一点没少；S3 意义不大（用户定），不为它动调度。
- 把 NDI SDK 的两条线程"拆到多核"：它们在 SDK 里，我们碰不到；SDK 自己没把 1080p60 压满一个核（20%）。
