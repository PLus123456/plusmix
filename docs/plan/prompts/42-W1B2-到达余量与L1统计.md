## 42 W1-B2 到达余量修正 + L1 统计（核心逻辑续做）
分支：w1-core-2（从 G3 合入后的 main 开）。只准动：Packages/SwitcherCore/Sources/SwitcherEngine/、Packages/SwitcherCore/Tests/SwitcherEngineTests/。
先读：reports/issues/W2A-w1-core-arrival-pacing-vs-camera-latency.md 全文（W2-A 的实测 + 末尾"G3 复核与裁定"，用户 2026-09-18 确认按裁定改）；
Packages/SwitcherCore/Sources/SwitcherEngine/Slots/ArrivalPacing.swift、LockFreeFrameSlot.swift（`latest(forTick:)`）；设计方案 §3.2 挑帧规则、§3.6；docs/contract-changes/005（引擎侧算法一节）；reports/w1-core.md §4 第 13 条。

背景：到达余量是 G2 为合成源的 V4 加的引擎内部机制，理论对（余量 ≥ 窗口最大到达延迟才不与到达赛跑），但三处实现缺陷让摄像头（到达延迟 55 ms 固定 + 几 ms 抖动）
在产品配置下 L1 2.5–3.9 帧、起流黑屏 4.2 s（对照契约入口 0.53 帧）。契约不动（`FrameSlot.latest(atOrBefore:)` 语义不变），不改测试图案 / 阈值。

交付（裁定第 2 条，逐条都要）：
1. 初值 = 第一帧 d₀ + 保护带，不再乘 `initialFactor`（d ≤ 0 的源仍走 `initialFloor`）。
2. 饿死保护，热身期也生效：候选表满、最旧候选仍不合格、这一拍没有可返回的帧 → 立即把余量降到让最旧候选此刻恰好合格。任何情况下槽里有帧时 `latest(forTick:)` 不得返回 nil。
3. 余量的动态上限 = 窗口最小到达延迟 + 一个节目帧 + 保护带（替换 min(500 ms, d_min + (capacity − 1) × 输入帧长)）：任何源的到达余量代价 ≤ 1 个节目帧；更晚的帧按"迟到"路径（一次 dup、不丢帧、不再抬余量）。
4. 保护带比例部分按抖动跨度（窗口 d_max − d_min）算，不按 d_max 绝对值。
5. 估计器窗口：改按时间定长的块（例如 8 × 2 s）或对超过上限的样本不计入窗口最大值；取舍自己定，写进报告。
6. 可选：`Engine.registerInput(number:slot:pacing:)` 允许组装方按输入类型给 `PacingOptions`。
7. 提案 005 的引擎侧（P2 落地字段之后做；若本会话先于 P2，把数据放 `EngineCounters` 并留好接口，P2 后补一行）：`RenderInputTable` 旁每路 256 项预分配环记 (tick, ingressTime, sequence)，
   `renderer(_:didComplete:)` 调第一个消费者前取 now，新帧才累加 sum / count / max（同一帧重复使用的拍不算），`StatsAssembler` 每秒算窗口平均与最大值。渲染线程零分配。

  余量 16 s 内回落；60 fps 同延迟源同样的断言。
