# Mac 原生导播台（代号 Switcher）设计方案 v0.1

目的：把"走 C 路线、自研核心 + 拼库"变成可以开工的设计。范围是第一版：引擎、主界面、控制接口。文中的延迟、性能数字都是目标值，验收口径以《导播台测试标准》为准。

---

## 0. 先回答：借鉴别人的设计思路行不行

行，但要分清四样东西：

| 东西 | 能不能用 | 说明 |
|---|---|---|
| 思路、功能划分、交互范式（PGM/PVW、编号输入、叠加通道、T-bar、线程模型、统计口径） | 能 | 思路不受著作权保护。硬件导播台几十年都是这套 M/E 范式，vMix、Nageru、ATEM 都在用 |
| 别人的代码 | 看许可证 | 见下文 |
| 图标、皮肤、字体、截图、文档原文 | 不能 | 这些是作品 |
| 名字、商标 | 不能 | 产品名和宣传里别带 vMix / OBS 字样；"兼容 vMix API"这种描述性用法上线前问律师 |

许可证决定你能复制什么代码，所以先定许可证：

- 选 Apache-2.0（推荐）：能直接用 HaishinKit（BSD-3）、AudioKit（MIT）、Syphon（BSD）、libsrt（MPL-2.0）、libsamplerate（BSD-2）、libebur128（MIT）、FFmpeg 的 LGPL 构建（动态链接）。不能复制 OBS（GPLv2）和 Nageru（GPLv3）的代码，但可以读它们的文档和源码学思路，自己重写。NDI、DeckLink 这类闭源 SDK 没有任何麻烦。
- 选 GPL：能复制 OBS / Nageru 的代码（保留版权声明；v2 和 v3 的兼容性看各自 COPYING 里有没有 "or any later version"）。代价是闭源 SDK 和 GPL 主程序一起发布有争议，OBS 的做法是把 NDI 做成独立插件动态加载，你也得这么做。
- 推荐 Apache-2.0 的原因：拼的库全是宽松许可证；闭源 SDK 不用绕；商业公司和设备厂商愿意贡献兼容性代码，而设备兼容性是这个项目最大的风险；专利条款对你有利。

以上不是法律意见。

## 1. 产品定义

一句话：Apple Silicon 原生的多机位导播台，用导播（PGM/PVW）范式，服务教会、学校、活动公司。

### 1.1 统一用词

| 词 | 意思 |
|---|---|
| Input（输入） | 编号的信号源：摄像头、采集卡、屏幕、文件、图片、NDI、纯音频 |
| Program / PGM | 观众看到的画面 |
| Preview / PVW | 下一个要切上去的画面 |
| Transition（转场） | PVW 变成 PGM 的方式：Cut、Fade、Wipe、Zoom、Stinger |
| T-bar | 手动控制转场进度的推杆 |
| FTB | 渐黑（Fade to Black） |
| Overlay 1–4（叠加通道） | 叠在 PGM 上、可独立开关的一层：下三分之一字幕、画中画、台标。对应 ATEM 的 DSK |
| Bus（音频总线） | Master、Bus A、Bus B、Headphones |
| Output（输出） | 录制、推流、NDI 发送、外部显示、虚拟摄像头、多画面 |
| Tally | 每个输入"在 PGM / 在 PVW / 都不在"的状态 |
| Show（节目文件） | 一个 JSON 文件，保存输入、布局、音频、输出配置 |
| Tick | 节目时钟的一拍，等于一帧的时间 |

### 1.2 第一版做什么

- 输入：摄像头 / UVC 采集卡、DeckLink（SDI/HDMI）、屏幕和窗口、视频文件、图片、NDI 接收、纯音频设备。
- 切换：PGM/PVW、Cut / Fade / Wipe / Zoom、T-bar、FTB、Overlay 1–4（画中画、下三分之一）、基础抠像。
- 音频：每输入增益 / 静音 / 延迟补偿 / EQ / 压缩，四条总线，音频跟随视频（AFV），EBU R128 响度表，耳机监听。
- 输出：录制（H.264 / HEVC / ProRes，可 ISO 分路录）、推流（RTMP / RTMPS / SRT，多目的地）、NDI 发送、第二屏全屏输出、虚拟摄像头、多画面。
- 控制：快捷键、MIDI、Stream Deck、本地 HTTP + WebSocket API、可选的 vMix API 兼容层。
- 无界面模式（headless）：引擎不带 UI 也能跑，测试和自动化用。

### 1.3 第一版明确不做

标题设计器、回放 / 慢动作、虚拟演播室、远程连线（WebRTC）、脚本、10-bit / HDR、多画布（横竖同出）、插件系统。这些都放到后续，每一项的设计见《导播台后续方案》；架构上要给它们留位置（见第 12 节）。

## 2. 架构总览

```
输入层                      合成层（Metal）                    输出层
────────                    ─────────────                     ──────
摄像头/UVC ─┐                                                 ┌─ 显示：PVW / PGM / 多画面 / 外部屏
DeckLink ───┤  每路输入：                                      ├─ 编码器（VideoToolbox）─► 录制 / 推流
屏幕/窗口 ──┤  采集线程 ─► 帧槽(最新 2–3 帧)                   ├─ NDI 发送
文件/图片 ──┤              │                                  ├─ 虚拟摄像头（CMIO 扩展）
NDI ────────┤              ▼  每个 tick：                      └─ 多画面
音频设备 ───┘        取每路"最新一帧" ─► 合成 PVW 纹理
                                    ─► 合成 PGM 纹理 ─► 转 NV12 ─► 派发（IOSurface，零拷贝）

音频：每路输入 ─► 异步重采样到 48 kHz ─► 混音（四条总线）─► 效果 ─► 输出设备 / 编码 / 录制 / NDI
控制：UI · 快捷键 · MIDI · Stream Deck · HTTP/WS ─► 命令总线 ─► 状态机 ─► 状态快照 ─► 所有消费者
时钟：节目时钟（host time，固定帧率 tick）驱动合成；音频设备时钟驱动音频回调；所有帧都按 host time 打戳
```

### 2.1 一帧的旅程（以 UVC 摄像头 → 推流为例）

1. 采集回调拿到一帧（CMSampleBuffer，IOSurface 背后的 NV12 像素缓冲），把它的时间戳换算成 host time，放进该输入的帧槽。
2. 节目时钟到了第 n 拍。渲染线程从每路输入的帧槽里挑"时间戳 ≤ 第 n 拍时刻"的最新一帧。
3. 渲染线程用 Metal 把 PGM 输入、转场、叠加层画成 PGM 纹理，再画 PVW 纹理和多画面纹理，提交 GPU。
4. GPU 画完，PGM 纹理经一个 compute kernel 转成 NV12，落在一个 IOSurface 上。
5. 这块 IOSurface 同时交给：编码器队列、NDI 队列、虚拟摄像头、录制器。谁慢谁自己丢帧，不许拖住渲染线程。
6. 编码器输出的 H.264 包带着"第 n 拍的时刻"作为 PTS，进入 RTMP 封装，发出去。
7. 各显示窗口按各自显示器的刷新率，把"最新画完的 PGM 纹理"复制到屏幕。显示不在节目时钟里。

## 3. 线程与时钟（核心中的核心）

参考 OBS 的三线程模型（渲染、视频输出/编码、音频各一个线程），改成适合 Metal 和 Core Audio 的版本。

### 3.1 节目时钟

- 基准是 mach_absolute_time（host time）。按节目帧率生成理想拍点：t_n = t_0 + n × T。59.94 fps 时 T = 1001/60000 s，用有理数算，不要用浮点累加。
- 等待用 mach_wait_until 或 leeway 为 0 的 DispatchSource 定时器，每拍都对照理想拍点校正，不累积误差。
- 渲染线程要是在下一拍到期时上一帧还没提交，就跳过这一拍，记一次"渲染滞后丢帧"（口径同 OBS 的 missed frames due to rendering lag）。

### 3.2 渲染线程

- 每拍做的事：读一次状态快照 → 为每路输入挑帧 → 录制命令缓冲区（PGM、PVW、多画面）→ 提交 → 提交完成回调里把 PGM 派发出去。
- 三重缓冲，用信号量把 CPU 领先 GPU 限制在 2 帧以内。所有纹理、命令缓冲区来自池子，每帧零分配。
- 挑帧规则：取时间戳 ≤ 当前拍点的最新帧。输入是 30 fps 而节目是 60 fps，同一帧自然被用两次；输入是 59.94 而节目是 60，每 1000 帧重复一次。这就是帧率转换和时钟漂移的全部处理，不需要别的机制。
- 每路输入的帧槽最多留 2–3 帧（Nageru 的经验：不共时钟的设备之间必然有相位差和漂移，所以每路都需要一个小队列吸收抖动；队列越深延迟越大）。

### 3.3 显示与渲染解耦

- OBS 的 Metal 后端踩过的坑：CAMetalLayer 最多 3 个 drawable 在途，渲染线程若直接等 drawable，会被显示器刷新率卡住，预览掉帧。
- 做法：渲染线程只画到离屏纹理。每个显示窗口用 NSView.displayLink(target:selector:) 按自己显示器的刷新率，把最新完成的纹理 blit 到自己的 CAMetalLayer。CVDisplayLink 已被苹果弃用（macOS 15 起标记），不要用。
- 输入缩略图窗口用低刷新率（15–30 fps）省 GPU。

### 3.4 输出分发

- PGM NV12 IOSurface 派发给每个消费者各自的队列（编码、NDI、虚拟摄像头、录制）。每个消费者有自己的线程。
- 消费者处理不过来时丢自己队列里的旧帧，并记"编码滞后跳帧"（口径同 OBS 的 skipped frames due to encoding lag）。
- 编码 PTS 用"拍点时刻"，不用"渲染完成时刻"。这样各线程负载波动不影响 A/V 同步。

### 3.5 音频线程

- 输出设备的 IOProc 回调是系统给的实时线程。回调里只做：从各输入环形缓冲取样、重采样、混音、效果、写输出、更新表。
- 回调里禁止：加锁、分配内存、打日志、Swift 的引用计数抖动（用不安全指针或 C 写热路径）。跨线程用无锁 SPSC 环形缓冲和原子量。
- 混音块大小等于设备 buffer size（默认 256 帧 @ 48 kHz ≈ 5.3 ms）。
- 每混完一块，把这块的首样本 host time 作为音频 PTS，交给编码 / 录制队列。

### 3.6 时钟对齐

- 所有进来的视频帧和音频块，一律在入口换算成 host time 打戳。AVCapture 的时间戳用 CMSyncConvertTime 转到 host clock；DeckLink 用回调给的参考时间加上入口时的 host time 校准；NDI 收到时打戳，另加一个小抖动缓冲。
- 视频靠挑帧吸收不同设备的时钟差。
- 音频靠每路一个异步重采样器：跟踪该输入的实际到达速率和输出设备时钟的比值，动态微调重采样比（±0.1% 量级），把输入设备的时钟"拉"到输出设备时钟上。Nageru 就是这么做的。
- 每路输入可设手动延迟补偿（0–500 ms），修采集卡自身的 A/V 偏差。

### 3.7 延迟预算（内部）

输入帧槽 1–2 帧 + 合成 1 帧 + 显示 ≤ 1 帧，内部约 3 帧（60 fps 下 50 ms）。加上设备自身延迟后的端到端目标见测试标准 L 系列。

## 4. 数据模型

```swift
struct Frame {                 // 视频帧
    let pixelBuffer: CVPixelBuffer   // IOSurface 背后，NV12 或 BGRA
    let pts: HostTime                // 入口打的戳
    let duration: HostTime
    let color: ColorInfo             // BT.709 / BT.2020，limited / full
}

final class Input {            // 一路输入
    let number: Int
    var name: String
    let kind: InputKind          // camera / decklink / screen / file / image / ndi / audio
    var state: InputState        // live / noSignal / error
    let videoSlot: FrameSlot     // 采集线程写，渲染线程读，最多 3 帧
    let audioRing: AudioRing     // SPSC 环形缓冲
    var settings: InputSettings  // 延迟补偿、裁切/变换、音频路由、增益、效果链
}

struct MixerState {            // 不可变快照，每拍读一次
    var program: Int
    var preview: Int
    var transition: TransitionState   // 类型、时长、进度（自动或 T-bar）
    var ftb: Bool
    var overlays: [OverlayState]      // 4 个：输入号、开关、位置尺寸、进出动画
    var audio: AudioState             // 各总线、各输入路由、AFV 开关
    var outputs: [OutputState]
}
```

- 节目文件（Show）就是上面这些的 JSON 序列化，带 schemaVersion，老版本要能读。
- 状态修改只走命令（第 10 节）。渲染线程和音频线程只读快照，靠原子指针交换拿到最新的。

## 5. 合成引擎（Metal）

- 输入纹理：NV12 缓冲通过 CVMetalTextureCache 直接变成 Y、CbCr 两张纹理，片段着色器里转 RGB。不在 CPU 上转格式。
- 工作色彩空间：第一版 BGRA 8-bit（BT.709 gamma 域直接混合）。简单、够用，代价是叠加半透明时和线性域略有差别。第二版换 16-bit float 线性中间纹理（Nageru 的做法），到时只改合成 pass，接口不变。
- 每拍的合成步骤：
  1. PGM 底：PGM 输入（带裁切、缩放、变换）。
  2. 转场中：把"旧 PGM"和"新 PGM"按进度 t 混合（Fade 是 mix，Wipe 是遮罩，Zoom 是变换插值，Stinger 是带 alpha 的视频叠加）。
  3. Overlay 1 → 4 依次叠上（各自的位置尺寸、进出动画进度）。
  4. FTB：乘一个黑色比例。
  5. PVW = PVW 输入（可选预览叠加层）。
  6. 多画面：各输入缩略图 + PGM + PVW 画进一张纹理，带 tally 边框和名字。
- 转场只在拍点边界发生；Cut 是原子换输入号，不存在半帧状态。
- 抠像：YCbCr 空间的颜色距离 + 溢色抑制，第一版够用。
- 缩放：第一版下采样用 mipmap + 双线性，第二版换 Lanczos（MPSImageLanczosScale 或自写）。
- 输出转换：RGB → NV12（BT.709 limited range）的 compute kernel，写进 IOSurface 供编码。
- 所有着色器都能离线跑（给一个状态和一组输入图，画出一张 PNG），这是测试标准里画面正确性用例的前提。

## 6. 输入层

统一接口：每路输入自带线程，只往自己的帧槽 / 环形缓冲里写，从不碰渲染线程。

| 类型 | 用什么 | 要点 |
|---|---|---|
| 摄像头 / UVC 采集卡 | AVCaptureSession + AVCaptureVideoDataOutput | 请求 NV12（'420v'），alwaysDiscardsLateVideoFrames = true；时间戳转 host time |
| DeckLink SDI / HDMI | Blackmagic DeckLink SDK（C++，用 ObjC++ 桥接） | 开格式自动检测；无信号事件要处理；帧数据要拷一次进 IOSurface（无法避免）；内嵌音频一起拿 |
| 屏幕 / 窗口 | ScreenCaptureKit | 直接给 IOSurface 背后的缓冲；macOS 13+ 还能抓系统音频 |
| 视频文件 | AVAssetReader + VideoToolbox 硬解 | 文件是"时钟从属"：按节目时钟出帧，不按自己的时钟；支持循环；音频解到环形缓冲 |
| 图片 | 一次性解码成纹理 | PNG 带 alpha；大图预缩放 |
| NDI | NDI SDK for Apple（recv） | UYVY / BGRA 转纹理；到达时打戳；小抖动缓冲 |
| 纯音频 | Core Audio 输入设备 / 聚合设备 | 只进音频环形缓冲 |
| 合成测试源 | 引擎内置 | 烧入帧号、输入 ID、闪光帧；测试标准依赖它 |

- 无信号：每路输入有期望帧间隔，超过 N 倍没新帧就进 noSignal 状态，画面显示黑场或最后一帧加提示，不阻塞。
- 热插拔：监听设备连接通知，设备回来自动恢复，输入编号和设置不变。
- 第二版加：Syphon、远程连线（WebRTC）、浏览器源。

## 7. 音频层

- 引擎：自写混音循环，跑在输出设备的 IOProc 里，不用 AVAudioEngine 做主图（动态增删输入、实时线程可控性、多总线都是自写更省心）。效果用苹果自带的 AudioUnit（ParametricEQ、DynamicsProcessor、PeakLimiter），在自己的循环里调 AudioUnitRender。AudioKit 的 DSP 内核作为备选。
- 内部格式：48 kHz、float32、非交错。
- 重采样：libsamplerate（BSD-2），支持动态改比率，用于第 3.6 节的时钟对齐。苹果的 AUVarispeed 是备选。
- 总线：Master、Bus A、Bus B、Headphones。每路输入：增益、静音、独听（送耳机）、声像、延迟补偿、送哪些总线。
- AFV（音频跟随视频）：切换时相关输入做交叉淡变，长度等于转场时长，起点和视频转场同一拍。
- 表：峰值 + 真峰值 + EBU R128 瞬时 / 短期 / 积分响度（libebur128，MIT）。
- 监听：耳机总线可选 PFL / AFL，目标延迟 < 10 ms（buffer 128–256）。
- 出口：Master 送编码（AAC，AudioToolbox）、录制（多轨：各总线和各输入 ISO 音轨）、NDI、系统输出设备。

## 8. 输出层

| 输出 | 用什么 | 要点 |
|---|---|---|
| 编码 | VideoToolbox VTCompressionSession（H.264 / HEVC） | RealTime 开、AllowFrameReordering 关（无 B 帧）、MaxKeyFrameInterval、AverageBitRate + DataRateLimits 做准 CBR；每个输出一个会话，多个会话共享同一块 NV12 IOSurface |
| 录制 | AVAssetWriter | 第一版写 QuickTime .mov 并设 movieFragmentInterval（1 s），崩了也能恢复到最后一个片段（OBS 换成混合 MP4 就是为这个）；停止后可选转封装成 MP4；ProRes 用硬件；ISO 分路录制每路一个 writer，同一拍起步，共用 PTS |
| 推流 | HaishinKit（BSD-3，RTMP / RTMPS / SRT / WHIP） | 每个目的地独立会话、独立重连（指数退避），一路断不影响其他路；它既能接未压缩帧自己编码，也可能只用它的连接与封装层——做到这一步时验证接哪一层，若不能直接送已编码帧，就自己封装 FLV / MPEG-TS 只借它的协议层 |
| NDI 发送 | NDI SDK（send，async） | PGM 必送，各输入可选；音频一起 |
| 外部显示 | 全屏 NSWindow + CAMetalLayer，displayLink 驱动 | 可选 PGM / PVW / 多画面 / 任一输入（相当于 Aux） |
| 虚拟摄像头 | CMIO Camera Extension（macOS 12.3+） | 主程序通过 IOSurface + XPC 送帧；需要系统扩展签名和公证，开发期用 systemextensionsctl developer on |
| 多画面 | 合成引擎的一张纹理 | 可送外部显示、独立窗口、NDI |

每个输出都暴露统计：帧数、丢帧、码率、重连次数，进状态快照，UI 底栏和 API 都读同一份。

## 9. 控制层与 API

### 9.1 单一状态机

- 一个 actor 持有状态。所有修改都是"命令 → 应用 → 生成新的不可变快照 → 发布"。UI、快捷键、MIDI、API 都只发命令，不直接改状态。
- 渲染线程每拍读一次最新快照。切换因此永远落在拍点边界，线程安全也简单。
- 命令示例：cut、fade(duration)、setPreview(input)、setProgram(input)、tbar(progress)、ftb、overlay(n, on, input)、audioGain(input, dB)、mute、startRecord、stopRecord、startStream(dest)、setInputSetting(...)。

### 9.2 本地 API

- HTTP + WebSocket，JSON。GET /api/v1/state 全量状态；POST /api/v1/command 发命令；WS 推送状态增量和 tally。
- 这是官方接口，Stream Deck 插件、MIDI 映射、Companion 模块都对着它写。

### 9.3 vMix 兼容层（可选，独立模块）

- 提供 HTTP GET /api/?Function=Cut&Input=1 这类调用和 /api 的 XML 状态，以及 TCP 文本协议（FUNCTION / TALLY / XML / ACTS 子集）。
- 做成适配器：vMix 函数名映射到内部命令，没实现的返回明确错误。只实现 Companion 的 vMix 模块用到的子集。
- 好处：用户现成的 Companion / Stream Deck 配置第一天能用。风险：法律灰区，发布前问律师。

### 9.4 其他控制

- 快捷键：可配置。定义自己的默认表（数字键选 PVW，Shift + 数字直切 PGM，空格 Cut，回车 Fade，F 键 FTB），别照抄别人的表。
- MIDI：CoreMIDI；T-bar 映射 CC，按钮映射 Note。
- Stream Deck：官方 SDK 插件调本地 API，或直接走 Companion。
- Tally：状态推送里带每路输入的 PGM / PVW 状态，供多画面边框、Stream Deck 按钮颜色、外部 tally 设备用。

## 10. 界面层

- AppKit 主窗口，NSSplitView 分区，布局按上一轮的示意图：上面 PVW / PGM 双监，中间转场 + T-bar + FTB + Overlay，下面编号输入缩略图，右侧可收起的音频调音台，底部输出栏和状态行。
- 监视器和缩略图都是 NSView + CAMetalLayer，用 displayLink 各自刷新。缩略图低刷新率。
- SwiftUI 只做设置、表单类面板（NSHostingView 嵌入），不做实时视频视图。
- 多画面和外部输出各自独立窗口。
- 状态行：fps、渲染耗时、GPU、丢帧、编码器占用、推流码率、磁盘剩余。这些数字和 API 里的是同一份。

## 12. 关键决策记录

| # | 决策 | 为什么 | 替代方案 |
|---|---|---|---|
| 1 | 输入取"最新帧"，队列只留 2–3 帧 | 延迟最低，帧率转换和漂移自动解决 | 深队列按 PTS 严格排（延迟大，只有全 SDI 同步锁相环境才值得） |
| 2 | 显示与渲染解耦 | OBS Metal 后端的教训：等 drawable 会被显示器节流 | 渲染线程直接呈现（掉帧） |
| 3 | 单状态机 + 命令总线 | 切换必在拍点边界，线程安全简单，API 与 UI 天然一致 | 各处直接改状态（必出竞争条件） |
| 4 | 不用 SwiftUI 做实时视图 | 性能和刷新控制不够 | 全 SwiftUI（掉帧） |
| 5 | 自写混音循环 + 苹果 AudioUnit 效果 | 实时线程可控，动态增删输入不抖 | AVAudioEngine 做主图（重连接时有毛刺） |
| 6 | 第一版 BGRA 8-bit，第二版 float16 线性 | 先把管线跑通 | 一上来 float16（多一层复杂度） |
| 7 | 第一版录制用带片段的 .mov | 崩溃可恢复，AVAssetWriter 现成 | MKV（苹果生态难用）、自写混合 MP4（第二版） |
| 8 | Apache-2.0 + 闭源 SDK 独立 target | 见第 0 节 | GPL |
| 9 | 先 headless 跑通核心循环，再做 UI | 风险全在管线；UI 是体力活 | 先做 UI（会在最后发现性能问题） |
| 10 | 编码 PTS 用拍点时刻 | A/V 同步不受线程负载影响 | 用渲染完成时刻（同步会漂） |

## 13. 性能与延迟目标

参考机器两台：M1 MacBook Air 8 GB（下限）、M2 Pro Mac mini（目标机）。

| 场景 | 目标 |
|---|---|
| 1080p60，8 路输入（2 UVC + 1 SDI + 1 NDI + 2 文件 + 1 屏幕 + 1 图片），2 路推流 + 1 路录制 + NDI 发送 + 多画面 | Air 上：渲染 ≤ 4 ms/帧，GPU ≤ 50%，CPU ≤ 60%，1 小时丢帧 ≤ 5 |
| 4K30，4 路输入，1 路推流 + 1 路 ProRes 录制 | Mac mini 上同样阈值 |
| 端到端延迟（含设备自身） | UVC 摄像头 ≤ 100 ms，SDI ≤ 70 ms，NDI ≤ 120 ms，屏幕 ≤ 50 ms |
| 命令到 PGM 生效 | ≤ 1 拍 + 网络往返 |
| 长稳 | 8 小时无崩溃、无音频断裂、A/V 漂移 ≤ 5 ms |

细化的定义、测法、必须 / 目标两档阈值见《导播台测试标准》。
