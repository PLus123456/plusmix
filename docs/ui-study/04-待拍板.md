### Q01【C 转场列】转场按钮改成"转场 1–4 四个可配置槽"，还是保持"一个按钮 = 一种效果"？

- **选项**
  - **A 四个槽，进契约**（R3a）：转场列 = Cut / 转场 1–4 / FTB。每个槽存效果、时长、Wipe 参数、Stinger 参数；点主体执行，点 ▾ 或右键改配置、不执行。出厂 1 = Fade 0.5 s、2 = Wipe 1 s、3 = Zoom 1 s、4 = Stinger 1 s，和今天的四个按钮等价。
    - 契约：TransitionState 加 slots（恰好 4 个）和 currentSlot，加 setTransitionSlot / useTransitionSlot 两条命令（R3a C 附 3），命令数 34 → 36；旧节目缺 slots 时补出厂值。
    - 工作量 L：契约、reducer、CommandCatalog / Validator / api.md、快捷键与 MIDI 动作、兼容层 Transition1–4 / SetTransitionEffect1–4 / SetTransitionDuration1–4、App 转场列；Stream Deck 按钮可以晚点。
    - 操作员：同一种效果能有不同时长（"Fade 0.5 s"和"Fade 2 s"并存），最多四套 Stinger；快捷键 / MIDI / Stream Deck / API 能一键打出任一槽；删输入时 reducer 统一清掉槽里的 Stinger 引用。
  - **A′ 四个槽，只存在 App 里**（R5-E4；也是 R3a 写的"提案不批时的过渡做法"）：界面和 A 一样，槽配置存 Show.layout；点一个槽 = App 同一轮发 setTransitionParams + setTransition + autoTransition。

    - 契约：不改。工作量 S–M。
    - 操作员：几乎不用重新学；但所有效果共用一个时长，只有一套 Stinger；一键打 Wipe 仍要靠控制层的"组合动作"（R5-M02）。
- **倾向**：三份报告三种说法。R3a 选 A：外部控制都要按槽触发，参考的函数表就是 1–4 各一套（图 084），一拍内原子完成，reducer 能统一清引用。R5 选 A′：不想为此动契约。R8 选 B：不加按钮宽度，离 T-bar 最近。

### Q04【F 设置体系】四个设置窗要不要合成一个带侧栏的"设置"窗？改动怎么生效？

- **现状**：偏好设置（一张长表单 9 节）、输出设置（左侧 7 页）、快捷键、MIDI 映射四个窗互不相干，快捷键 / MIDI 挂在"切换"菜单下；三种提交方式混用，关窗时没应用的改动静默丢掉（R1-M02、R1-M04）。
- **卡住什么**：设置区重做（R1 估 L）；工具条"设置▾"、底栏各 ⚙、输入 / 叠加 / 音频设置入口最后落到哪个窗。
- **选项**
  - **(a) 合成一个"设置"窗**（R1-E1）：侧栏分两组——"本节目"（节目格式、输出各页、节目音频，随节目文件保存）和"本机"（常规、音频设备、远程控制、Tally、快捷键、MIDI、性能与电源、更新与诊断），页头写明存在哪；⌘, / 工具条 / 各 ⚙ 打开同一个窗的对应页；换引擎时窗不关，只重新绑数据。契约不改。L。操作员：一个入口；"改了设置、换个节目又没了"这种事看得懂为什么。
  - **(b) 窗还分开，只理入口**（R3a-E10）：快捷键… / MIDI 映射… 挪出"切换"菜单，放到 App 菜单"设置…"下面；工具条"设置▾"列出所有设置窗。契约不改。S。操作员：窗还是好几个，本节目 / 本机分不清。
  - **(c) 折中**（R5-M06；也是 R3a-E10 的另一选项）：偏好设置里加"控制"页（快捷键 / MIDI 两个子页，以后放触发器），输出设置窗照旧独立。M。
- **提交方式**（R1-E2；R6-M10、R7-M12 同一口径，列在这里一起认）：即时生效（mac 惯例，输出设置现在就是这样）；要换引擎的项（节目格式、节目音频、音频设备、API / 兼容层端口、PVW 全部叠加）集中到一个"应用并重起引擎"，录制 / 推流进行中先确认；快捷键 / MIDI 表有没保存的改动时，关窗或切页先问。另一种是照参考 OK / Cancel，没人选。

  - 要定的是视频码率：(i) 固定 6 Mb/s（现状，1440p60 偏低）；(ii) 跟节目格式走。汇总给的起点（按每像素每帧约 0.15 bit）：1080p30 ≈ 10 Mb/s（约 4.5 GB/小时）、1080p60 ≈ 18 Mb/s（约 8 GB/小时）、1440p60 ≈ 32 Mb/s（约 14 GB/小时）、2160p30 ≈ 36 Mb/s（约 16 GB/小时）；音频 AAC 256 kb/s。这些数只是起点，你定。
- **推流**（R7-E5、R7-M08）
  - 现状：H.264 6 Mb/s、尺寸跟节目（可能是 1080p60 或 4K）、关键帧 120 帧（30 fps 下是 4 s，超出常见平台要求）、AAC 160k。参考默认 720p 2.5 Mb/s。
  - (i) R7 的方案：尺寸封顶 1080p，60 fps 给 6 Mb/s、30 fps 给 4.5 Mb/s，关键帧 2 s，AAC 160k，质量预设里带 720p 档。
  - (ii) 更保守：默认 720p 3 Mb/s，1080p 做成一键档。
- **倾向**：R6 没给数；R7 给了 (i)，同时问要不要 (ii)（教会 / 学校上行常见只有 5–10 Mb/s）。
- **建议**：录制选 (ii) 跟节目格式走。推流选 (i)，再加两点：第 2 个起的目的地默认"与推流 1 相同"（R7-M09）；推流页底下显示一行"合计上行约 n Mb/s"——每个目的地各起一个编码器、各占一份上行（R7-G06），两个目的地就是两倍，这比默认值保守不保守更容易出事。你的用户要是大多上行很弱，就选 (ii)。契约不改（App 新建输出时自己给默认值，契约默认值不动）。
- **旧决定**：不涉及。**补截图**：不需要。

## 6. 调研会话补充的 3 条（核对与目视检查的新发现，汇总时还没收进上面）

### Q66【C / 引擎】转场进行中，改 PVW / PGM 要不要拦？

- **现状**（核对 VF1 §4 第 8 条，调研会话复核属实）：状态机对 fade / setTransition / setTransitionParams / autoTransition 都有"转场进行中就拒收"，但 setPreview / setProgram 没有（`Packages/SwitcherCore/Sources/SwitcherEngine/State/MixerReducer.swift:99-104`）。渲染器在转场中按**当前**的 program 画底、按**当前**的 preview 画切入画面（`Packages/SwitcherCore/Sources/SwitcherRender/Renderer/CompositorPasses.swift:246-256`）。结果：转场中按数字键或点缩略图，正在切进来的画面被换掉；Shift + 点缩略图，正在切出去的底图被换掉——PGM 上是可见的跳变。
- **卡住什么**：格子上的"转场 / Cut"按钮（01a D4）要按同一口径判断；测试标准 V6"切换准确性"的口径。
- **选项**
  - **(a) 转场中拒收 setPreview / setProgram**：最像硬件台，最安全。只改 reducer 两行 + 用例；API 客户端会收到"被拒"（和 autoTransition 同一口径）。契约：命令语义变了，要在 docs/CONTRACTS.md 写一句，走小提案。
  - **(b) 收下，但这次转场按开始时的两路走完，完成后再生效**：操作员体验最顺，但状态里要多记"转场用的两路"，契约 + 渲染器都要改（M）。
  - **(c) 维持现状**，在手册写明"转场中别换 PVW"。
- **建议**：(a)。操作员在转场中按数字键很常见，现在的后果直接上 PGM；(b) 更好但改动大，可以以后再做。
- **旧决定**：不涉及落地方案 §7；是引擎状态机（W1-B）的规则。
- **来源**：R3b-M14（setPreview 部分）、核对 VF1 §4 第 8 条；问题单 reports/issues/UIA-w1-core-preview-program-change-mid-transition.md。

### Q67【A / P】退出时要不要把当前状态静默写回已打开的节目文件？

- **现状**（VF1 §4 第 5 条）：新建 / 打开前不保存也不自动存，未保存的改动直接丢；退出时却把当前状态静默写回已打开的节目文件（`App/Sources/AppController.swift:111-115`），同时还存一份 LastSession。两条路径语义相反；手册只写了"未保存的节目自动存到 LastSession"。
- **选项**
  - **(a) 统一成"问"**：有未保存改动时，退出、新建、打开都弹"保存 / 不保存 / 取消"（mac 文档类 App 的惯例，配合 window.isDocumentEdited 标出来）；LastSession 照存，给崩溃恢复用。S。
  - **(b) 统一成"自动存"**：新建 / 打开前也静默写回原文件（像 macOS 自动存储的文档）。S。风险：试着改一下又不想要时，原文件已经被改了。
  - **(c) 维持现状**，手册写清楚。
- **建议**：(a)。节目文件常被当成模板反复用，静默覆盖会把模板改坏；配合 01a A3。
- **来源**：核对 VF1 §4 第 5 条；01a A3；问题单 reports/issues/UIA-w3-app-show-switch-and-quit-safety.md。

### Q68【P / 发布】X01–X05（一步操作就停掉直播、事先不确认）按不按 S0 处理？

- **现状**：02 功能缺口第 1 节把 X01（底栏录制 / 推流一按全停）、X02（起不来的推流路让"推流"按钮变成全停）、X03（新建 / 打开直接停录制推流）、X04（偏好设置里三个"应用"直接换引擎）、X05（删除正在推的目的地不确认）按测试标准 §6 字面的"输出停止"标成了 S0。
- **选项**
  - **(a) 按 S0**：0.1.0 放行前必修（docs/KNOWN_ISSUES.md:5 规定 S0 / S1 不许出现在已发布版本的表里）。五条都是 S 级工作量：停止前确认（01a E11）、起不来的路单独显示并可单路重试（L2、L13）、换 session 前确认（A3、F5）、在推的路锁住删除（L12）。
  - **(b) 按 S2**（有绕过办法：操作员小心、按钮本来就是做这件事）：记进 KNOWN_ISSUES，下一版修。
  - **(c) 拆开**：X02 按 S0（操作员想重试，结果停掉了正常的路，是误导造成的中断），其余四条按 S2。
- **建议**：(a)。它们都是现场一次误点就断播的路径，修起来小；如果 0.1.0 的时间更紧，至少按 (c) 先修 X02 和停止前确认。
- **来源**：02 功能缺口 X01–X05；R1-M06、R7-M02、R3a-M19、R1-M05、R7-M12。
